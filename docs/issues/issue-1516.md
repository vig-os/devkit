# [Issue 1516]: [[BUG] Agent-fingerprint check blocks the release PR when the CHANGELOG describes an Actions-bot-identity bug](https://github.com/vig-os/devkit/issues/1516)

### Description

The 1.10.0 release train blocked at its first CI run: the `Commit Messages` job's *Check PR title and body for agent fingerprints* step failed on the release PR (#1515) with:

> PR title or body contains blocked AI agent fingerprint: 'github-actions&#91;bot&#93;'. Remove agent identity from the PR.

Two mechanisms interact:

1. `prepare-release.yml` generates the release PR body from the frozen CHANGELOG section, and `release.yml`'s finalize refreshes it from the same source.
2. In `contains_agent_fingerprint` (`packages/vig-utils/src/vig_utils/utils.py`), the **emails** blocklist — which includes the Actions bot identity — is matched as a bare, case-insensitive substring over the whole content. The attribution-context guard from #274 (only match on lines saying "authored by", "generated by", …) applies **only to names**, not emails.

The 1.10.0 CHANGELOG entry for #1503 accurately *describes* a bug in which a push ran under the Actions bot identity, naming it literally (in backticks, as prose). That literal rode into the PR body and tripped the check. Any future changelog entry that documents a bot-identity bug will re-trigger this: the check punishes precise incident description.

### Steps to Reproduce

1. Land a changelog entry under `## Unreleased` that names the Actions bot identity literally (e.g. describing an auth bug).
2. Run `just prepare-release X.Y.Z`.
3. CI on the draft release PR fails in `Commit Messages` → *Check PR title and body for agent fingerprints*.

### Expected Behavior

A descriptive prose/code-span mention of a bot identity in a generated PR body does not block the release train. The email list should get the same contextual treatment names got in #274 (attribution-context lines only), or code spans should be stripped via `allow_patterns` before matching.

### Actual Behavior

`Commit Messages` fails on the release PR; the train cannot proceed to candidate publish until the CHANGELOG is reworded.

### Environment

- CI (`ci.yml`, `Commit Messages` job), release PR #1515, branch `release/1.10.0`
- Failing run: https://github.com/vig-os/devkit/actions/runs/31807433196/job/94789618674

### Additional Context

Immediate fix-forward for the 1.10.0 train (this issue's bugfix PR): reword the #1503 entry in `CHANGELOG.md` on `release/1.10.0` to say "the default GitHub Actions identity" instead of the literal, so the generated PR body is clean. `dev` needs no edit — the post-promote sync merge carries the reworded `[1.10.0]` section back cleanly (dev's copy stays at the merge base).

Checker-side hardening (contextual email matching or code-span stripping) is the durable fix and can land in a later milestone; scoping it here keeps the train's diff minimal.

# [Comment #1]() by [c-vigo]()

_Posted on August 14, 2026 at 03:33 PM_

Remediation record for the 1.10.0 train:

1. PR #1517 reworded the CHANGELOG entry on `release/1.10.0` (merged).
2. The release PR body (#1515) was regenerated by hand via `gh pr edit` — prepare-release snapshots the CHANGELOG into the body and only finalize refreshes it, so the merge alone did not fix the body.
3. A rerun of CI run 31812605374 still failed: **workflow reruns replay the original frozen event payload**, so `github.event.pull_request.body` predated the body edit. Reruns can never pick up a PR-body edit.
4. PR #1515 was closed/reopened to fire a fresh `pull_request` event with the corrected body → new CI run fully green (13/13).
5. `release.yml` validate then still refused the candidate: it counts every FAILURE check run in `statusCheckRollup` on the head SHA, and the superseded run's two FAILURE runs (Commit Messages, Test Summary) were still attached alongside the green run. Since that run was unfixable by construction (frozen payload), **run 31812605374 was deleted** (`gh run delete`) to make the rollup reflect the operative green run. Its failure content is fully described above and in this issue.

Checker-side hardening remains open here. A possible second follow-up: validate's rollup check could consider only the latest check run per name (as `gh pr checks` does) to tolerate superseded runs.
