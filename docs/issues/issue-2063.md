# [Issue 2063]: [DEVKIT_UPGRADE_EXCLUDE is ignored by install.sh and scaffold-drift: a disabled 'release' feature prunes a consumer-owned (cargo-dist) release.yml](https://github.com/vig-os/devkit/issues/2063)

## Summary

With `DEVKIT_FEATURES_DISABLED=release`, the scaffold treats `.github/workflows/release.yml` as a disabled-feature path and deletes it on every `--force` (`feature_paths release` → `Pruning .github/workflows/release.yml for disabled feature 'release' (#1284)...`). That's right for devkit's own `release.yml`. It's wrong when the consumer's `release.yml` belongs to another tool: in vig-os/tessera it is generated by cargo-dist, which has no setting to rename the file.

`DEVKIT_UPGRADE_EXCLUDE` only partly covers this. It's honored by exactly one path, `devkit-upgrade.yml`, which runs `git checkout --` on the listed paths after the scaffold. Neither of the other two paths reads it:

1. **`install.sh --force` run by hand**: deletes the consumer's `release.yml`. The operator has to notice the deletion and restore it. Observed on 1.19.0, vig-os/tessera#771.
2. **`ci.yml`'s `scaffold-drift` job**: re-scaffolds a clone and diffs it, so the pruned `release.yml` always shows up as drift. The consumer's only options are `DEVKIT_DRIFT_CHECK=false`, which switches off the drift gate for *every* managed file, or a permanently red gate.

So a repo whose release workflow comes from another tool can't have a working drift gate.

## Reproduce

1. A direnv consumer with `DEVKIT_FEATURES_DISABLED=release`, `DEVKIT_UPGRADE_EXCLUDE=.github/workflows/release.yml`, and a cargo-dist `.github/workflows/release.yml`.
2. Run `curl -sSfL https://raw.githubusercontent.com/vig-os/devkit/refs/tags/1.19.0/install.sh | bash -s -- --force --version 1.19.0 .`.
3. `git status` shows ` D .github/workflows/release.yml`.
4. Set `DEVKIT_DRIFT_CHECK=true` and open a PR: `Scaffold Drift` fails with that deletion as its diff.

## Expected

A path listed in `DEVKIT_UPGRADE_EXCLUDE` is consumer-owned for every scaffold entry point: install.sh, the devkit-upgrade workflow and scaffold-drift. The prune never deletes it, and the drift diff never reports it. Possible fixes:

- have `init-workspace.sh` skip excluded paths in both the copy and the disabled-feature/retired prunes, so one rule covers all three callers; or
- add a narrower knob for a consumer-owned file that sits at a managed path.

Either way, the `.vig-os` comment for `DEVKIT_UPGRADE_EXCLUDE` should say which entry points honor it. Today it reads as if the upgrade honors it everywhere.

## Context

- vig-os/tessera#441 is why tessera runs with `DEVKIT_DRIFT_CHECK=false`. tessera#771 (the 1.19.0 adoption) keeps it off for this reason alone: a local re-run of the scaffold-drift recipe shows `release.yml` as the only drift apart from one documented local patch, which is upstream #1902.
- Related: #1783 (managed cargo-dist lane), #1284 (feature opt-outs), #1296 (`DEVKIT_UPGRADE_EXCLUDE`).
