# [PR 1611](https://github.com/vig-os/devkit/pull/1611) fix(security): reconcile both exception registers against landed remediation

## Description

Reconciles both CVE exception registers against remediation that has already
landed. Nothing is renewed or re-dated here: every entry removed is one that no
longer matches a finding, and every entry kept was re-verified against a live
scan.

- **`.vulnixignore`** — the 8-entry rsync block (`Expiration: 2026-09-23`) is
  deleted 16 days before its expiry. The weekly pin advance `c5c4a43b` →
  `c25784012c` (#1609) ships **rsync 3.5.0**, past all 17 advisories of the
  2026-09-01 batch.
- **`.trivyignore`** — the three surviving blocks (`CVE-2026-42504`,
  `jwt-token`, `CVE-2026-32316`/`CVE-2026-40164`) are retired. All three were
  written against the Debian `:latest` image, whose Trivy job left with the
  Debian path (#642); the Nix image inherited the file but none of the findings.

Both files keep tombstones in place of the deleted entries, per the register
convention, so the history of why an exception existed and how it died stays
in the file.

## Changes Made

### `.vulnixignore`: the rsync block dies on remediation

The block was placed **earliest** on the staggered grid precisely because its
remediation lever moved soonest: the fix needed one `staging-next-26.05` →
`release-26.05` → `nixos-26.05` hop (NixOS/nixpkgs#557467), which the weekly
`update-nixpkgs.yml` advance then picks up on its own. That is exactly what
happened, one grid period early.

Evidence — the first nightly scan on the new closure (run `34108767776`, dev
lane, checkout `1867537d` = the merge of #1609):

| | `dev` (new pin) | `main` (old pin) |
|---|---|---|
| rsync | **absent** | `rsync-3.4.4`, 17 CVEs |
| glibc | `2.42-84` | `2.42-67` + `2.42-84` |
| delta | **17 removed, 0 added** | — |

`rsync` is still a direct member of the image env (`flake.nix`), so this is
remediation, not a closure change; the locally built closure on this branch
contains `rsync-3.5.0`.

The other **14 entries were re-checked in the same pass and every one still
matches a live finding** — glibc ×6 (10-14), zlib/sqlite/libmicrohttpd ×5
(09-30), fzf ×2 (10-07), shellcheck CPE mismatch (2027-06-23). None is renewed
or re-dated; the remaining grid is unchanged.

`main` still ships rsync 3.4.4 and keeps the block until the next release train
carries the pin and the register over together, so this opens no gap there.

### `.trivyignore`: retired to an empty register

Each entry had its own reason to be gone, and none of the three could ever have
fired against the Nix image:

- **`CVE-2026-42504`** (#512, #564) — Go stdlib MIME header DoS, matched via the
  `gh` binary Debian shipped on Go 1.26.3. Every gobinary in the Nix image
  reports **stdlib v1.26.7**, past the 1.26.4 rebuild the block was waiting for.
- **`jwt-token`** (#512) — secret-scan false positive on a JWT-like string in
  typos crate test fixtures under `/opt/pre-commit-cache`. The Nix image has no
  such path (prek caches at `/opt/prek-cache`) and ships typos as a prebuilt
  binary, not its source fixtures.
- **`CVE-2026-32316` / `CVE-2026-40164`** (#805, #512) — jq DoS/RCE scoped to
  Debian `jq`/`libjq1` 1.6-2.1+deb12u1. The image has no dpkg DB for Trivy's OS
  scanner and ships jq 1.8.2. The block's own escape condition was "time-box the
  ignore until the Nix image ships" — it has.

The file itself is kept, not deleted: it stays the seam for genuine Nix-image
Trivy findings and secret false positives (`docs/CONTAINER_SECURITY.md`). With
no entries, `check-expirations` has nothing to expire.

### Manual Testing Details

Registers are config, so the verification is the scan evidence itself:

1. **vulnix gate, edited register vs the new closure's findings** —
   `gh run download 34108767776 -n nix-image-cve-scan-dev`, then
   `uv run vulnix-gate vulnix-findings.json --register .vulnixignore` →
   `No unexcepted HIGH/CRITICAL findings (CVSS >= 7.0); 14 exception(s) applied`.
2. **Register-vs-findings reconciliation** — every one of the 14 surviving
   entries matches a live finding in that artifact; the 8 removed ones match
   none.
3. **Trivy, with no ignore file** — `nix build .#devkitImage` on this branch,
   then `trivy image --input result --scanners vuln,secret --severity
   HIGH,CRITICAL,MEDIUM` (trivy 0.72.0 from the pinned nixpkgs; CI runs 0.74.0):
   63 unique vulnerabilities, **0 secret findings**, and none of
   `CVE-2026-42504`, `CVE-2026-32316`, `CVE-2026-40164` present. The secret
   scanner is confirmed enabled in that run's log.
4. `uv run check-expirations .trivyignore .vulnixignore` → green;
   `prek run --all-files` → green.
5. `just test` → **1169 passed, 3 skipped, 2 failed**. Both failures are local
   environment artefacts, not this diff, which touches only the two registers
   and the changelog pair:
   - `test_image.py::TestFileStructure::test_manifest_files` — checksum
     mismatch on `/root/assets/workspace/.pymarkdown` between the working tree
     and the locally cached image, which predates `8e7c4916` (the pymarkdown
     fixer change on `dev`). CI builds the image from the branch and does not
     see it.
   - `test_integration.py::TestDevContainerCLI::test_github_cli_authentication`
     — needs a host `gh` token forwarded into the devcontainer.
