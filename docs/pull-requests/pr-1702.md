# [PR 1702](https://github.com/vig-os/devkit/pull/1702) ci: split Project Checks into parallel lanes

## Description

`Project Checks` was the only job on CI's critical path and a serial chain of
independent work: 9m59s on run
[36108278820](https://github.com/vig-os/devkit/actions/runs/36108278820) while
every other job finished by 8m37s. Nothing after `setup-env` consumed another
block's output — prek, BATS, pytest and the nix gates each read the checkout and
the warm dev-shell and nothing else — so the job cost the **sum** of its blocks
rather than the longest one.

This splits it into four parallel lanes (`Project Lint`, `Project Tests`,
`Project BATS`, `Project Flake Gates`), each running `setup-env` once and one
block, with the `test-project` composite as the single source of truth for every
block body. The critical path becomes setup + the longest block.

## Changes Made

**1. The composite owns every block (`.github/actions/test-project/action.yml`).**
The seven flake gates (Tier 0 `nix-fast-build`, flake output schema, dev-shell
contracts, hooks fidelity + services, capability modules, downstream stub, zizmor
audit) lived inline in `ci.yml` — in the composite's only caller. They moved into
the composite verbatim (each body gaining the `shell: bash` a composite step
requires) under a new `flake` suite value, and the BATS and pytest blocks gained
their own values. `suite` is now a single enum: `all | lint | bats | pytest |
flake`, with `all` unchanged. Coverage summary + upload are guarded to `pytest`
(nothing else produces `coverage.xml`) and the prek cache to `lint`.

`setup-env`'s `sync-dependencies` is derived from the suite
(`inputs.suite == 'bats' && 'false' || 'true'`) rather than exposed as a caller
input: the environment a block needs is a property of the block. The bats block
needs the flake toolchain but never the project venv — verified: `init.bats` only
probes `command -v uv`, the `uv sync` strings in `init-workspace.bats` are heredoc
payloads, and `just.bats`/`init-workspace.bats` stub the binary.

An unrecognized `suite` is refused by a first, toolchain-free step
(`::error::unknown test-project suite '<value>'`). Every block is guarded on an
exact match, so a typo in a lane (`flakes`, `tests`) would run **nothing** and
report the lane green — the one silent-pass mode a per-lane split introduces that
the serial chain could not have. The static half of the same gap is pinned in
`tests/test_workflow_summary_gate.py`: each lane passes the block it is named
for, no two lanes pass the same block, and every block the composite guards (bar
`all`) is some lane's suite, so a block cannot be implemented with no job running
it.

I did **not** add the optional `bats-files` input that would let a later matrix
split the BATS lane without touching the composite: it costs a word-splitting
`$BATS_FILES` and a `shellcheck disable` for a split the issue itself says to
measure first. YAGNI — it is a two-line change when that measurement happens.

**2. Four lanes (`.github/workflows/ci.yml`).** `project-lint` (15 min),
`project-tests` (15), `project-bats` (15), `project-flake` (25 — it keeps the old
chain's budget for a cold-Cachix dev-shell rebuild). The short lanes are sized for
`setup-env`, not for their block: a `flake.lock` change that misses Cachix builds
the dev-shell in every lane rather than once, so 15 minutes buys that headroom
four times over. Each lane carries the
*unchanged* `workflow_dispatch` gate
(`inputs.test-suite == 'all' || … == 'project'`), so a dispatch of `project` still
runs all four, and each keeps its own checkout (a local `uses: ./…` is resolved
from the workspace before the composite's own checkout runs).

**3. `summary` fans in over all four.** `needs:`, the four echo lines and four
failure/cancelled legs. `skipped` stays tolerated. This is load-bearing: with
`if: always()` a lane left out of `needs:` is not merely unchecked, it is
*invisible* to the only required status check.

**4. Docs.** `docs/WORKFLOW_SECURITY.md` names `project-flake` as the job running
the zizmor regression gate (that file is hand-written, not generated from
`docs/templates/`). `zizmor.yml`'s own header pointed a reader at
`.github/workflows/ci.yml → "Audit managed workflows"`, where that step no longer
lives; it now names the composite step and the `project-flake` lane that runs it.

That correction could not be confined to the root file: `assets/workspace/zizmor.yml`
is **not** hand-edited — `sync-manifest` regenerates it from the root copy and only
prepends the managed banner, so the hook rewrites the mirror (and fails the commit)
the moment the root text changes. Both files therefore carry the same comment-only
edit; no rule changes, so a consumer sees one line of header drift on their next
upgrade and no behavior difference. Deferring the fix instead would have meant
leaving the pointer wrong in the file a maintainer actually reads.

Archival `docs/issues/*`, `docs/pull-requests/*` and released CHANGELOG entries
that mention "Project Checks" are left as the historical record they are.

## Additional Notes

**Two of the issue's acceptance criteria need correcting.**

*Rulesets:* the criterion assumes a ruleset names `Project Checks`. It does not.
`gh api repos/vig-os/devkit/rulesets` shows Dev protection and Release protection
requiring only `Test Summary`, and Main protection requiring `Test Summary` +
`CodeQL Analysis (actions)` + `CodeQL Analysis (python)`. The aggregate absorbs
the rename, so **no `org-config` change is needed** and no aggregate job has to be
kept for the check name.

*Scope:* the criterion says only `.github/**` changes. This PR also touches
`tests/test_workflow_summary_gate.py` (the exact `needs:` set — deliberately not
relaxed to a subset), `tests/test_workflow_zizmor_baseline.py` (the zizmor gate
now lives in the composite) and one line of `docs/WORKFLOW_SECURITY.md`. All three
are consequences of the rename, none is a consumer artifact.

*Lane:* this targets `dev`, not the release-neutral lane (#1676) — `main` does not
yet carry the `bats -j` wrapper from #1690, so the drvPath-identity guard has no
matching base there. It ships with the next train.

Three prose comments still say "project-checks" where the lane is now named —
`flake.nix:1221`, `tests/test_utils.py:459` and `tests/test_install_script.py:5`
(the complete live set; `grep -rn project-checks` over non-archival files finds no
others). All three read correctly as generic descriptions of "the cheap project
lane", none is a path or a job reference a tool resolves, so they are left out of
this diff rather than widening it further.

Follow-up the issue predicted: `Security Scan` is now the whole-run bottleneck
(build-image 1m57s → security-scan 6m28s = 8m25s on the same run). Filed as #1701.
