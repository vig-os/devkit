# [PR 1596](https://github.com/vig-os/devkit/pull/1596) feat(ghdash): per-view section lists for gh-dash profiles

## Description

`vigos.ghdash.profiles` named one section list per profile and the wrapper wrote
it to **both** `prSections` and `issuesSections`. PR and issue queues are not
filtered alike — `review-requested:@me`, `draft:false`, `reviewed-by:@me` either
do not apply to issues or mean something else — so a profile written for pull
requests landed a permanently empty section under Issues, and the only escape
was writing the profile down to the intersection of what both views understand.

The quieter half: `templateText` set both keys unconditionally, so a consumer
who tuned `programs.gh-dash.settings.issuesSections` kept it for bare `gh-dash`
and lost it in **every** `gh-dash-repo` launch, `default` included — which is
the launch path a `vigos.sesh` layout's `prs` window actually uses.

- [x] `feat` -- New feature

### Modifiers

- [ ] Breaking change (`!`) -- This change breaks backward compatibility

## Changes Made

- **`profiles` takes either shape.** A profile is still one entry — one
  dashboard — but may now be `{ prSections; issuesSections; }` instead of a
  bare list. `issuesSections = null` (the default) mirrors `prSections`;
  `[ ]` leaves the issues view empty rather than wrong. A bare list coerces to
  today's meaning, so nothing written against #1586 changes.
  - Implementation note: the issue's sketch used `coercedTo sectionList …`, but
    nixpkgs asserts `coercedType.getSubModules == null`, so the source type is
    shape-only (`listOf anything`) and the entries are type-checked by
    `prSections` after coercion — a malformed section still fails at eval
    (verified: `profiles.bad = [ { title = "X"; typo = true; } ]` errors with
    ``The option `vigos.ghdash.profiles.bad.prSections."[definition 1-entry 1]".typo` does not exist``).
- **`templateText` takes the pair** and stops folding one list into both; issue
  filters are scope-free and get the `__GH_DASH_SCOPE__` placeholder exactly as
  PR ones do.
- **`default` stops overwriting the consumer's issues view.** The module only
  `mkDefault`s `programs.gh-dash.settings.issuesSections`, so anything else is
  the consumer's own dashboard and passes through verbatim — those sections
  carry the scope their author chose; one that wants to follow the launch repo
  writes the placeholder itself (documented on the option).

Scope note: the same "respect the consumer's value" rule is deliberately *not*
applied to `prSections`, per the issue — the generated sections are PR-shaped
and scoping them to the launch repo is the wrapper's whole purpose.
