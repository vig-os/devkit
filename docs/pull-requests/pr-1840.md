# [PR 1840](https://github.com/vig-os/devkit/pull/1840) docs: document how a flake consumes a devkit project's packages

## Description

A flake that consumes a devkit project's `packages` (e.g. one binary from a Rust CLI built by `mkRustProject`) inherits devkit's whole input tree in its lock: home-manager twice, git-hooks, treefmt, process-compose, services-flake and a second nixpkgs. This PR documents, and puts under test, how the **consuming** flake avoids that.

**Stack 6/6** for #1833. Base: #1839 (`bugfix/1826-preflight-untracked-build-output`).

## Type of Change

- [x] `docs` -- Documentation only
- [x] `test` -- Adding or updating tests

## Changes Made

The issue offered two remedies. I measured before choosing:

| downstream flake | lock nodes | package store path |
| --- | --- | --- |
| plain `my-tool.url` | 17 | `…b87d0…-consumer_matrix_rust-0.1.0` |
| + `nixpkgs` follows (the issue's dedupe stanza) | 17 (nixpkgs is now the consumer's) | same |
| + `follows = ""` on the 7 devkit inputs packages never read | **8** | **same** |

- **Docs (taken):** new `docs/MIGRATION.md` section "Projects that ship packages to other flakes", with the full consumer stanza: build with the consumer's nixpkgs, and empty the seven unused devkit inputs with Nix's `follows = ""` idiom. That leaves `nixpkgs`, `crane`, `fenix` and `flake-utils`. The two stub flakes (`assets/workspace/flake.nix`, `assets/flake.d/rust.flake.nix`) get a comment pointing there.
- **Template flip (not taken):** making `vigos` follow the project's `nixpkgs` would re-pin devkit's tools, overlay and dev shell onto a nixpkgs devkit never tested or cached. The issue's own caveat says this needs a guard. Since the consumer-side stanza fully solves the reported problem, the flip isn't needed. The rationale is in the doc section.
- **Contract test** `tests/test_flake_package_consumers.py`:
  - It executes the documented block **verbatim** from MIGRATION.md, only swapping in local URLs, against a project rendered from the `#rust` template plus the seeded `mkRustProject` flake, with `vigos` overridden to this checkout. It must build.
  - A second test asserts that the stanza's drop list equals devkit's inputs minus the four a package needs. A new devkit input therefore fails CI until the doc covers it.

## Changelog Entry

### Changed
- **Documented, tested stanza for flakes that consume a devkit project's packages** ([#1832](https://github.com/vig-os/devkit/issues/1832))
  - New `docs/MIGRATION.md` section "Projects that ship packages to other flakes": the consuming flake builds the package with its own nixpkgs and drops the devkit inputs a package build never reads (`follows = ""`), so its lock shrinks from devkit's whole input tree to `nixpkgs`, `crane`, `fenix` and `flake-utils`
  - CI builds a Rust project's package through that exact block, and fails if devkit adds an input the stanza does not cover or starts reading one it drops. The scaffolded `flake.nix` keeps following devkit's nixpkgs, and points at the section
