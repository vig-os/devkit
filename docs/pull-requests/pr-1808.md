# [PR 1808](https://github.com/vig-os/devkit/pull/1808) feat(ci): take the resolve-toolchain runner from a repository variable

## Description

The `resolve-toolchain` job in all seven scaffolded workflows that declare it now takes its runner from the repository or organization variable `DEVKIT_CI_RESOLVE_RUNNER`:

```yaml
runs-on: ${{ vars.DEVKIT_CI_RESOLVE_RUNNER || 'ubuntu-26.04' }}
```

`vars` resolves server-side before any runner is provisioned, so this avoids the chicken-and-egg problem that rules out `.vig-os`. When the variable is unset, the job stays on the hosted default, so nothing changes for existing consumers. A private consumer can opt in to stop paying one billed hosted minute per workflow run.

## Changes Made

- `assets/workspace/.github/workflows/{ci,sync-issues,sync-main-to-dev,abandon-release,prepare-hotfix,promote-release,release}.yml`: the `resolve-toolchain` `runs-on` is now overridable by the variable (one line each). I also updated `ci.yml`'s header comment.
- `assets/workspace/.vig-os`: the `DEVKIT_CI_RUNNER` comment now points the resolve jobs at the variable.
- `docs/MIGRATION.md`: the "some jobs always stay hosted" limitation is replaced with a section on the variable. It covers how to set it, that the value is one label and not a list, that **nothing validates it**, and that it is **not an outage fallback**.
- `tests/test_ci_runner.py`: the two "stays hosted" asserts are replaced with a parametrized check over all seven workflows. A completeness test also fails if a scaffolded workflow adds a `resolve-toolchain` job that is missing from the list.

### Validation (the issue's second spike point)

The issue asks for validation in `resolve-toolchain` or documentation of the failure mode. Validating in the job isn't possible: the job is the thing waiting for a runner, so an unmatched label queues and never fails. I documented the failure mode instead, along with the fix that needs no commit (`gh variable delete DEVKIT_CI_RESOLVE_RUNNER`).
