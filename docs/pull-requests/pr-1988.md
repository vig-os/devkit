# [PR 1988](https://github.com/vig-os/devkit/pull/1988) fix: advance lockstep release pins during upgrades

## Description

A consumer upgrading a release-pinned devkit input could receive new scaffold hooks while retaining the old dev shell, preventing the adoption commit and PR. The target installer now advances release pins that matched the pre-upgrade DEVKIT_VERSION by default, using the existing atomic pin/lock update.

## Type of Change

- [x] `fix` -- Bug fix
- [x] `test` -- Adding or updating tests

### Modifiers

- [ ] Breaking change (`!`) -- This change breaks backward compatibility

## Changes Made

- Capture the pre-upgrade version. Empty DEVKIT_FLAKE_PIN_ADVANCE advances lockstep release pins; true advances any release pin; false opts out and is preserved.
- Normalize refs/tags/ and a leading v for comparisons. Preserve refs/tags/ and the URL form; remove v when advancing and report the spelling change in the single flake-bump line. Devkit publishes bare version tags.
- Check the actual retained pin after every outcome, including skipped updates, missing Nix, internal failures, and atomic rollback. Explicitly report an incomplete upgrade and lead with manual alignment and nix flake update, honoring an explicit false.
- Keep the warning rather than add another preflight detector: this preserves the opt-out and existing non-fatal installer contract while making the hook/CI failure and remedy explicit.
- The functional fix lives in the TARGET install.sh, which older consumer upgrade workflows already execute. It has no workflow-adoption prerequisite. The scaffold CI change only updates the error advice consumers see after adoption; the root CI has no corresponding gate.
- Update the default-change migration note, release guide, template comments, and Changed/Fixed changelog entries. Document the existing CI limitation: bare release refs are checked for equality; qualified refs receive the gate's warning. The installer recognizes both spellings.
