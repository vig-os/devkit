# [PR 1802](https://github.com/vig-os/devkit/pull/1802) feat: derive promote-release cleanup pattern from the configured pre-release format

## Description

Promote-release's best-effort cleanup pruned only `<prefix>X.Y.Z-rc[0-9]+` candidate tags. Since #1746 a repo can publish candidates in any `DEVKIT_PRERELEASE_FORMAT` (e.g. `alpha.{N}`), and those tags were never cleaned up — the cleanup pattern is now derived from the resolved format instead of hardcoded.

## Changes Made

- **vig-utils** (`packages/vig-utils/src/vig_utils/release_version.py`): new public `PreReleaseFormat.list_pattern(tag_prefix, version) -> str`, built on the same `re.escape`/placeholder-substitution machinery as the existing `_regex` helper (factored out into a shared `_pattern_body`) — no second placeholder parser. Unlike `_regex`'s internal named group, `list_pattern` emits a **plain POSIX ERE** (`(0|[1-9][0-9]*)`, `[0-9]{8}`): the pattern is handed to external tools (jq `test()`, `grep -E` in the cleanup job), and GNU `grep -E` neither expands `\d` nor correctly parses `(?:...)` — verified directly against the real binaries, not assumed. New CLI mode `release-version --list-pattern --version --format --tag-prefix` prints the anchored regex and reads no stdin; `--kind` is no longer unconditionally required.
- **Scaffold `assets/workspace/.github/workflows/promote-release.yml`** (not a synced copy — it's an original file served directly to consumers): `resolve-toolchain` re-exposes `prerelease-format`; the cleanup job's `PATTERN` now comes from `release-version --list-pattern`, replacing the hardcoded jq `gsub`-built regex and the `${RC_BASE}-rc*` git-ls-remote glob (now `${RC_BASE}-*` filtered through `grep -E "$PATTERN"`). The pattern reaches jq via `--arg pat`, never string-built into the filter. The existing "no GitHub Release" guard is unchanged.
- **Policy**: a tag from a *previously* configured format (a mid-series format switch) is intentionally **left alone** — only tags matching the CURRENTLY configured format are ever matched/deleted. Documented in the step comment and in `docs/DOWNSTREAM_RELEASE.md`.
- **Scope**: scaffold copy only. Devkit's own `.github/workflows/promote-release.yml` stays on literal `rc{N}` — it sets no `DEVKIT_PRERELEASE_FORMAT`, and its cleanup additionally prunes per-arch GHCR `-rcN-<arch>` tags that a format-generic matcher would not cover.
- Swept the rest of the scaffold (`release-core.yml`, `release.yml`, `release-extension.yml`, `devkit-upgrade.yml`, `plugins/devkit/skills/*`, abandon/prepare workflows) for any other hardcoded candidate-tag match the format change should have touched — found none; every other `rc` mention is either documentation/example text or already generic (`release-version` driven, candidate discovery over `X.Y.Z-*`).

### Changed

  ([#1749](https://github.com/vig-os/devkit/issues/1749))
  - The scaffolded `promote-release.yml` cleanup job used to prune only
    `-rc*` candidate tags, so a repo on a non-default
    `DEVKIT_PRERELEASE_FORMAT` (e.g. `alpha.{N}`, #1746) never got its
    candidate tags cleaned up. The match is now derived from the resolved
    format via the new `release-version --list-pattern` CLI mode

    existing `re.escape`/placeholder machinery rather than a second parser
  - A tag from a *previously* configured format (a mid-series switch) is
    intentionally left alone; the existing "no GitHub Release" guard is
    unchanged
  - Scope: the scaffold copy only. Devkit's own
    `.github/workflows/promote-release.yml` stays on literal `rc{N}` -- it
    sets no pre-release format and its cleanup also prunes per-arch GHCR
    `-rcN-<arch>` tags, which a format-generic matcher would not cover
