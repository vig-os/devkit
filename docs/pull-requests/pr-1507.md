# [PR 1507](https://github.com/vig-os/devkit/pull/1507) fix(ci): make the mirror-mode fold land and the promote reset safe

## Description

Fixes the two mirror-mode release defects surfaced by `vig-os/org-config` v1.1.0
— together, a data-loss path. They ship as **one PR** deliberately: both live in
the same `MANIFEST_SYNC_TARGET` rendering block of `assets/init-workspace.sh`,
and #1503 must not land ahead of #1502 (a working reset over a broken fold is
what deletes the archive). One PR makes that ordering unrepresentable.

## Type of Change

- [x] `fix` -- Bug fix
- [x] `test` -- Adding or updating tests

## Changes Made

**#1502 — the fold committed nothing, silently.** The path list reached
`commit-action` newline-separated; the action splits `FILE_PATHS` on commas, so
the whole blob was one nonexistent path, and it logged `No files to commit` and
returned **success**. The job printed "Folding 92 mirror archive path(s)" and the
release branch never moved.

- The list is now comma-joined from `git diff --cached --name-only -z`. The `tr`
  runs inside the pipeline because command substitution drops NUL bytes.
- That also fixes two latent mis-parses in the old
  `git status --porcelain | awk '{print $2}'`: porcelain C-quotes paths
  containing spaces, and renders renames as `R old -> new` (awk took the *old*
  path).
- A path containing a comma is unrepresentable in `FILE_PATHS`, so the step now
  **fails loudly** on one instead of mis-splitting it.
- `Re-pull release branch after fold` is now
  `Re-pull release branch and verify the fold landed`: it asserts the
  post-condition (the release branch carries the mirror's archive) rather than
  trusting the action's exit code. Deletions still don't propagate — archives
  only grow — so a release-only path is tolerated.

**#1503 — the reset 403'd, and would have deleted the archive if it hadn't.**
The job embedded the Commit App token in the push URL, but `actions/checkout`
persists its own credentials as `http.<host>.extraheader`, which outranks URL
userinfo. The push ran under the default Actions identity against
`contents: read` → 403 on every mirror-mode consumer, *after* the release was
already published.

- The App token is now generated **before** checkout and passed to it, so both
  the fetches and the push carry the App identity. `contents: read` stays
  deliberately — there's an inline comment saying so, since granting
  `contents: write` would "fix" a future 403 by silently moving mirror resets to
  the Actions identity.
- Note `persist-credentials: false` alone (the issue's suggested one-liner)
  would have fixed the push but broken the job's `git fetch` on **private**
  consumers, which have no anonymous read. Checking out *with* the App token
  fixes both halves and matches how `release-core.yml` already does it.
- **New guard, per the issue:** the force-push is gated on a new
  `Verify main carries the mirror archive` step that asserts main holds every
  `docs/issues` / `docs/pull-requests` path the mirror carries. Otherwise it
  skips with a `::warning::` — a stale mirror self-heals at the next nightly
  sync; deleted snapshots do not. The step's "a force reset loses nothing"
  comment is now true by construction.

## Testing

- [x] Tests pass locally (`just test`, `just test-bats`, `prek run --all-files`)
- [x] Manual testing performed (describe below)

Both defects passed review and CI because the only tests over this code are
**render pins** — they assert the steps exist, never that they work. That is the
part worth fixing structurally, so this PR adds
`tests/bats/release-mirror-fold.bats` (11 tests), which **extracts the rendered
`run:` blocks and executes them** against a throwaway repo whose `origin` is a
local bare clone: real `git fetch`/`checkout`/`diff`, real `$GITHUB_OUTPUT`, no
network. The fixture mirrors a consumer mid-release, including a spaced path and
a mirror-side rename.

Only the two steps that genuinely need GitHub are uncovered — `commit-action`
itself and the force-push — which is exactly why both are now gated on a
locally verifiable precondition instead of trusted.

RED-before-GREEN, against the unfixed renderer:

```
not ok 1 fold staging emits a single-line comma-joined path list (#1502)
not ok 6 fold staging fails loudly on a path commas cannot represent (#1502)
not ok 7 post-fold verification fails when the fold committed nothing (#1502)
not ok 9 mirror reset is refused when main lacks the archive (#1503)
not ok 10 mirror reset proceeds when main carries the archive (#1503)
not ok 11 mirror reset is refused when the mirror branch is absent (#1503)
```

All 11 green after the fix, as are the 6 mirror render pins (incl. the existing
`actionlint` pass over the rendered workflows) and the full 524-test bats suite.

## Additional Notes

**Rollout.** These steps are rendered at scaffold time, so the fix reaches
`vig-os/org-config` only through a `devkit-upgrade` adoption PR after the next
release. That is safe to wait for: with the 403 still in place, nothing is
deleted — the 403 is currently the only reason org-config's 55 issue files still
exist.

**Adjacent, deliberately not fixed here.** The `floating-tags` job in the base
`promote-release.yml` (`:669`) has the identical shape — token in the push URL,
default checkout, `contents: read` — so its comment about pushing "as the Release
App EXPLICITLY" looks unenforceable in practice. It is a different job and a
different token, out of scope for these two issues; happy to file it separately.
