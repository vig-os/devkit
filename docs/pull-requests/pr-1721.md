# [PR 1721](https://github.com/vig-os/devkit/pull/1721) fix(ci): give the guard's long steps their own timeouts and declare gate refusals

## Description

#1705 made gate 6 of `release-neutral-guard.yml` run on `!cancelled()` so a gate failure or an unlabel rewrites the sticky verdict. One residual of the same class stayed: the job's `timeout-minutes: 90` expiry *cancels* the job, so gate 6 is skipped and the last positive verdict stands over a run that proved nothing. Worse, the in-flight step's outcome under a timeout is `cancelled`, not `failure` — so even the `if:` widening the issue proposed would have fallen through to the **green** body, because the scan matched the literal `failure`.

Three changes, and one deliberate non-change:

- **Step budgets.** `setup` 10, `gate2` 10, `vulnix` 60 minutes — summing to 80, under the job's 90 — so a hang fails the *step* while the job lives on to reach gate 6 under the untouched `!cancelled()`. Measured on the one `.vulnixignore` lane run so far (set-up 41 s, gate 2 32 s, the extra 129 s), these are hang detectors, not tight budgets; the 60 leaves room for a cold-NVD rebuild of `main`'s closure.
- **Declared refusals.** The runner reports a step that exhausted its own budget as `failure` — indistinguishable from a gate refusing the change, so gate 6 would have called a gate 2 timeout "**gate 2** refused it". A refusal is now something a gate **declares**: each of the five gates writes `refused=true` to `$GITHUB_OUTPUT` on the path where it states its refusal (the vulnix extra only in its `vulnix-gate` branch, never in the scan-failure branch), and gate 6 reads them through a `REFUSED` env. The per-gate refusal wording is used only when the flag is set; every other non-green outcome — a failure with no declaration, a cancellation, an unrecognised value — is worded as infrastructure ("failed or timed out … before reaching a verdict"), naming the step and asking for a rerun. Erring that way costs a rerun; erring the other way tells a reviewer a gate refused a change it never examined.
- **Non-green scan.** Gate 6 now takes the first outcome that is neither `success` nor `skipped` (the two green outcomes are enumerated), so an unexpected outcome can no longer fall through to the positive verdict.
- **The `if:` is not widened.** With step budgets in place the only cancels left are a manual cancel and a lost runner, and for those skipping gate 6 is correct: a label run cancelled by hand must not have its real verdict overwritten by a refusal it never reached. Declined explicitly so the issue's proposal does not read as half-done.

### Fixed

- **A hung release-neutral guard no longer leaves its last positive verdict
  standing** ([#1712](https://github.com/vig-os/devkit/issues/1712))
  - The job's `timeout-minutes` expiry *cancels* the job, so gate 6 — which runs
    on `!cancelled()` — was skipped: a run that proved nothing left the previous
    "This change is release-neutral" comment as the pull request's only verdict,
    and a label-event run cannot even be superseded, so nothing else would
    rewrite it. The toolchain set-up, gate 2 and the `.vulnixignore` extra now
    carry their own step budgets (10, 10 and 60 minutes, summing to less than the
    job's 90), so a hang expires a *step's* budget first and the job survives to
    report it.
  - Which raises the opposite hazard, since the runner reports a step that
    exhausted its own budget as `failure` — indistinguishable from a gate
    refusing the change, and gate 6 would have called it "**gate 2** refused it".
    A refusal is now something a gate **declares**: each of the five gates writes
    `refused=true` where it states its refusal, and gate 6 words a refusal only
    where one was declared. Every other non-green outcome — a failure with no
    declaration, a cancellation, an unrecognised value — is reported as
    infrastructure, naming the step and asking for a rerun. The outcome scan also
    no longer selects on the literal `failure`, so an unexpected outcome can no
    longer fall through to the positive verdict.

## Additional Notes

- The timeout path cannot be exercised live; the stubbed-`gh` run and the shape tests are the evidence. The declaration relies on a failed step's `$GITHUB_OUTPUT` writes still being exposed as `steps.<id>.outputs` (standard runner behaviour); the next lane PR that trips gate 1 or 3 confirms it live.
- The reviewer's first pass caught that a step killed by its own `timeout-minutes` reports `failure`, not `cancelled` — the first version of this branch keyed the infrastructure wording on `cancelled` and would have mis-worded a gate 2 timeout as a refusal. The declared-refusal rule replaced it.
- The `setup` step is a `uses:` of a local composite action. GitHub does not support `timeout-minutes` on steps *inside* a composite; at the caller level it applies to the whole step, which is what is set here. The two steps that could realistically hang (`gate2`, `vulnix`) are plain `run:` steps.
