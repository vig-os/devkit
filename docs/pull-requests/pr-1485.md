# [PR 1485](https://github.com/vig-os/devkit/pull/1485) fix(smoke): bind the listener waits to the run they dispatched

## Description

The smoke listener's "trigger a workflow, then wait for it" pattern could match a
**stale, unrelated run** and report success without the dispatched run having
started. On the 1.8.0 final it made `Trigger and wait for release workflow` return
success in **1.5 seconds** — matching rc4's release run from 47 minutes earlier —
and promote-release was then fired against a repo that had no `1.8.0` release yet.

Silent on candidates (promote is skipped for RCs, so the defect hid across
rc1–rc4); fires on **every** final. The cross-repo gate then reports a false
negative, which is the worst failure mode for a gate.

## Type of Change

- [x] `fix` -- Bug fix

## Changes Made

The old guard assumed the newest run on `${WORKFLOW_REF}` at capture time was the
newest the poll would ever see other than the dispatched one. It is not: the
dispatched run needs a moment to appear in the API, and if the first poll lands in
that window, `--limit 1` returns a previous, already-`completed` run that is still
newer than a stale baseline.

All three call sites (prepare-release, release, promote-release) are fixed
identically and kept textually in lockstep:

- each trigger step stamps `DISPATCH_TS` immediately **before** `gh workflow run`;
- the wait accepts a run only if `createdAt >= DISPATCH_TS` **and**
  `databaseId > BEFORE_RUN_ID` — both guards must hold;
- capture and poll now carry identical `--workflow` / `--branch` /
  `--event workflow_dispatch` filters, so the baseline describes the population
  being polled;
- the **oldest** matching run is taken (ours is the first created after our stamp)
  and the id is **locked on**, so a later run cannot hijack the wait;
- the loop can never exit success without a bound run; the timeout stays a loud
  failure and now says no matching run was ever observed;
- the bound run's id and URL are logged, and both terminal messages name them.

`DISPATCH_TS` is backdated **60 s**: the stamp comes from the runner's clock and is
compared against a server-side `createdAt`, so skew in the wrong direction would
filter the dispatched run out of its own wait and turn every release into a
timeout. 60 s is ~47x smaller than the gap to the stale run that actually bit.

Two pre-existing bats tests asserted the **defective** guard verbatim, so they were
retargeted at the new shape (one now asserts the old guard is absent). Net test
count unchanged: 505 before, 505 after.

### Manual Testing Details

The new test module is not only shape assertions: it executes each wait step's real
bash against a stubbed `gh` that models the API visibility lag, replaying the 1.8.0
timeline. `test_stale_completed_run_is_never_accepted` runs the **pre-fix** bash
against those exact numbers and gets `exit 0` + "completed successfully"; the fixed
bash keeps waiting and binds to run `31604068811` once it appears.
