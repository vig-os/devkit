# [PR 2046](https://github.com/vig-os/devkit/pull/2046) fix: gate container-mode CI runners behind an opt-in key

## Description

Implements the owner decision on #2045: container-mode consumers (`devcontainer`, `both`) use `CI_RUNNER_*` runners only after they opt in with the new `.vig-os` key `DEVKIT_CI_CONTAINER_RUNNERS=true`. Without the key, every lane stays on hosted `ubuntu-26.04`, as in 1.18.x. `vars.CI_RUNNER_*` also resolves organization variables, and an expression cannot tell an inherited org variable from a repo one. An org that sets them for a pool with no container runtime therefore broke every container-mode repo in it on adoption: the 1.19.0-rc3 smoke test failed at `Initialize containers` and at Scaffold Drift's `docker run`.

Into `release/1.19.0`, because this blocks release 1.19.0 (#2033).

## Changes Made

**One gate, in `resolve-toolchain`** (`assets/workspace/.github/actions/resolve-toolchain/action.yml`)
- Parses `DEVKIT_CI_CONTAINER_RUNNERS` with the shared `KEY=VALUE` reader. The file is never sourced. Any value other than `true`, `false` or empty is an `::error::` and exit 1, in every mode, before any runner output is written.
- In `devcontainer`/`both` without `true`, the variable arm is skipped for every class. Each lane then gets the hosted default, so `DEVKIT_CI_LANE_SIZES` is ignored for placement, though it is still validated. The fork predicate still wins. The repo's own legacy `DEVKIT_CI_RUNNER` key keeps its 1.18.x meaning (see Notes).
- When the gate ignores a visible variable on a non-foreign run, the resolver prints one `::notice::` that names `CI_RUNNER_*`, the mode and `DEVKIT_CI_CONTAINER_RUNNERS=true`, and gives the reason. The partial-setup notice and the opted-in-class warning do not fire, because nothing is placed. The private-repo notice and the legacy-key migration warning also name the key. Under the gate, the migration warning lists only variables that are really unset, and it no longer says "delete the key once the variables are set": the key keeps deciding every class until the repo opts in. Labels are never printed.
- `direnv`/`bare`: unchanged.

**`devkit-upgrade.yml`**: its `upgrade` job runs `install.sh --docker` in every mode but direnv, so it needs a docker daemon. It now gets its runner from a new `resolve-toolchain` job (the same shape as `sync-issues`), not from `vars.CI_RUNNER_SMALL` directly. That job checks out the same `ref:` the upgrade rewrites (`dev`, or `main` after the trunk retarget), so the gate reads that branch's `DEVKIT_MODE` and opt-in key, not the default branch's. As with the key, a legacy `DEVKIT_CI_RUNNER` now places the upgrade job too; the consumer-matrix contract was updated to match. `report` also fires when `resolve-toolchain` fails (for example, an invalid key), because that failure skips `upgrade`.

**`init-workspace.sh`**: validates the key at the write path and writes it back on every upgrade. The legacy-key strip, decision (c)-1, now judges whether the key is inert with the gate applied. In a container mode without the opt-in, the variables place nothing, so the key is kept and a `ci-runner-migration:` line names the opt-in.

**Template `.vig-os`**: ships `DEVKIT_CI_CONTAINER_RUNNERS=` with a comment. **Consumer matrix**: the `ci-runner` cell runs mode `both`, so it now seeds `DEVKIT_CI_CONTAINER_RUNNERS=true`. That keeps it on the opted-in path and also exercises the write-back from start to finish.

Composite actions: only `resolve-toolchain` touches docker (the client-side probe above). `setup-devkit-toolchain` and `build-bundle` run inside the job's own container or on the host, and do not drive a daemon themselves. devkit's own `.github/` uses literal hosted labels and has no copy of the resolver, so there is nothing to keep in lockstep there.

`tests/test_ci_container_runners.py::test_container_jobs_take_the_gated_runner` derives the container-needing set from the workflows themselves: `container:` or `services:`, a `docker://` or `docker/*` action, any `docker`/`podman` CLI subcommand (full-line shell comments excluded), compose, `install.sh`, or a local composite action (`uses: ./…`, resolved one level, including through a sub-path checkout such as `./.devkit-resolve/…`) whose steps do any of these. It fails any such job whose `runs-on` is not the resolver's `runners` output, whether read directly from a resolver it `needs:` or through an `inputs.runners` that every caller fills from one. A future lane therefore cannot bypass the gate. The only exception is an explicit, commented allowlist of the nine resolver jobs (client-side registry probe, documented in ADR §5); a pinned test keeps each entry a resolver whose own definition needs no runtime besides that probe.

## Additional Notes

- **Legacy `DEVKIT_CI_RUNNER` under the gate.** The decision says "otherwise every lane runs on hosted `ubuntu-26.04`, as in 1.18.x", with the goal that no consumer breaks on upgrade. In 1.18.x the repo's own legacy key routed container-mode lanes on purpose. Honouring it is the 1.18.x behaviour, and it is the kind of explicit repo statement the decision asks for. Dropping it would silently move a self-hosted container-mode repo onto hosted runners, which fails on a billing-blocked org. So the gate ignores the inherited `CI_RUNNER_*` variables, not the legacy key. The legacy migration text and the upgrade strip both account for this, so following the migration never drops a repo onto hosted runners.
- **Known limit: what a self-hosted `CI_RUNNER_*` pool must provide, per mode.** The gate is keyed on the delivery mode, as decided.
  - `direnv`: no docker at all. Since #2040 the direnv Scaffold Drift step fetches the pin with `nix flake prefetch`, and the upgrade runs `install.sh` without a runtime; the pool needs `nix`, `jq` and `rsync`.
  - `bare`: `ci.yml`'s Scaffold Drift (`docker login`/`pull`/`run`) and `devkit-upgrade`'s `upgrade` (`install.sh --docker`) need a docker CLI and daemon. The gate does not apply in `bare`, so a `bare` repo whose pool has no container runtime still fails those two lanes. This needs its own issue (reported to the architect, not filed here).
  - `devcontainer`/`both`, gated: every lane is hosted, but the `resolve-toolchain` jobs still run on the direct `vars.CI_RUNNER_SMALL || vars.DEVKIT_CI_RESOLVE_RUNNER` expression and need a docker CLI (no daemon) for `docker login` / `docker manifest inspect`.
  - Documented in ADR §5 (Known limit) and MIGRATION.md (Container-mode CI runners).
- In container modes, `devkit-upgrade`'s new resolve job probes the image of the *current* pin, as every other resolve job in that repo does. The image cleanup deletes only untagged versions, so a pinned tag stays resolvable.
