# [PR 1751](https://github.com/vig-os/devkit/pull/1751) feat(plugin): ship the devkit Claude Code plugin

## Description

Ships a versioned **`devkit` Claude Code plugin**: eleven state-lookup-first operator skills for adopting vigOS devkit, running its release train, and keeping a consumer in sync. The plugin lives in this repository, beside the workflows it drives, and its version is devkit's own — so the skills and the verbs they wrap are released together and cannot drift.

The plugin is a thin operator surface, not a re-implementation. Every skill's step 1 is the read-only `/devkit:status` lookup, re-read in the same run; every mutating skill then carries a refusal table naming the state, why it is a foot-gun, and the verb that clears it; and the dispatch itself is always a canonical `just` recipe or workflow dispatch.

Two deviations from #1744's issue body, both required by the actual plugin format and [explained in full on the issue](https://github.com/vig-os/devkit/issues/1744#issuecomment-5869690313):

1. **`.claude-plugin/` holds only `plugin.json`.** The manifest reference is explicit that `skills/`, `commands/` and `hooks/` go at the plugin root, not inside `.claude-plugin/`. The issue's sketched `.claude-plugin/skills/…` layout would not load.
2. **Components are namespaced `plugin:component`**, so there is no bare `/devkit-status`. A skill `status` in plugin `devkit` is `/devkit:status`. Keeping the `devkit-` directory prefix would have produced `/devkit:devkit-status`.

Both manifests pass `claude plugin validate --strict`.

## Changes Made

**`plugins/devkit/` — the plugin (new)**

- `.claude-plugin/plugin.json` — id `devkit`, `version` = `1.17.0` = `DEVKIT_VERSION`.
- `README.md` — the command table, the five principles, and a pointer to `docs/RELEASE_CYCLE.md` as the source of truth ("when a skill and a doc disagree, the doc wins and the skill is a bug").
- `skills/status/` — the read-only report every other skill delegates to: scope (devkit vs consumer), the pin vs the latest release, scaffold drift, trains in flight, pre-release tags and whether a Release is attached, the promote gate gate-by-gate, the hotfix lane, `DEVKIT_WORKFLOW` vs the real topology (including the preserved-hook staleness of #1642), legacy-tag and tombstone hazards, and required App secrets. It matches a pre-release as `<base>-<anything>` and reads `DEVKIT_PRERELEASE_FORMAT`, so it stays correct once #1746 makes the format configurable.
- `skills/adopt/` — proposal only for a repo with no `.vig-os`: inspects languages, CI, existing release tooling, Nix and pre-commit; proposes `--mode` / `--workflow` / `--version` with reasons; renders the resulting manifest and the `--preview` diff; and flags the collisions that are silent rather than loud (release-plz, cargo-dist, semantic-release/release-please/changesets, an existing `flake.nix`, `.gitignore`, CodeQL, a preserved `.pre-commit-config.yaml`, gitflow with no `dev`).
- `skills/upgrade/` — `--preview` dry run first, always; applies only on an explicit second-turn confirmation; refuses through a dirty tree, a protected branch or a train in flight; calls out the `#1497` case where a flake input named something other than `vigos` is silently not bumped.
- `skills/release-{prepare,candidate,finalize,promote,abandon,hotfix,neutral}/` — one per pathway, each wrapping its canonical verb.
- `skills/pack-rust/` — read-only audit of what the Rust pack ships today (#1496) plus the silent-green trap; names #1746's three unmerged contracts as open work instead of describing them as available.

**`.claude-plugin/marketplace.json` (new)** — this repo is the marketplace (`vigos-devkit`), with a relative-path entry for `./plugins/devkit`. Installable on merge; when #927 lands, `vig-os/org-config` adds a `git-subdir` entry pointing here and nothing moves.

**`.github/workflows/release.yml`** — the finalize step that rewrites `.vig-os` now bumps `plugins/devkit/.claude-plugin/plugin.json` in the same place (nine added lines, self-contained).

**`tests/test_devkit_plugin.py` (new, 110 tests)** — see Testing below.

**`docs/RELEASE_CYCLE.md`** — a short "Operator plugin" subsection under Justfile Recipes.

  - Every skill starts with a read-only state lookup and carries an explicit

    another train in flight ([#1627](https://github.com/vig-os/devkit/issues/1627)),
    a floating tag that would move backwards
    ([#1626](https://github.com/vig-os/devkit/issues/1626)), a published

    ([#1301](https://github.com/vig-os/devkit/issues/1301)), a dirty tree,

    dispatches; they never re-implement release logic.
  - Read-only skills are model-invocable; every mutating skill sets
    `disable-model-invocation: true`, so an agent cannot infer its way into
    dispatching a release verb.
  - The plugin is versioned with devkit: `plugin.json`'s version equals
    `DEVKIT_VERSION`, and `release.yml`'s finalize step bumps both, so a
    consumer pinned to `X.Y.Z` gets the `devkit@X.Y.Z` skills.
  - Distributed through a marketplace in this repository
    (`/plugin marketplace add vig-os/devkit` then
    `/plugin install devkit@vigos-devkit`), not vendored into the consumer
    scaffold -- the per-repo copy is the drift model
    [#927](https://github.com/vig-os/devkit/issues/927) exists to retire.
  - `tests/test_devkit_plugin.py` fails when a skill names a `just` recipe or
    a workflow file that does not exist in devkit or in the scaffold.

## Testing

- [x] Tests pass locally (`just test`)
- [x] Manual testing performed (describe below)

`tests/test_devkit_plugin.py` — 110 tests, TDD (failing tests committed first in `27a3fd4f`, implementation in `c614d86d`). It enforces the two invariants that make drift impossible:

- **Version lock** — `plugin.json`'s version equals `DEVKIT_VERSION`, and a shape test asserts `release.yml`'s finalize step rewrites the plugin manifest in the same step that rewrites `.vig-os`. Without the second half the lock would hold only until the next release.
- **Referential integrity** — every `just <recipe>` and every `<name>.yml` token inside a code span or fenced block of any `SKILL.md` (and of the README) must resolve against devkit's justfiles/workflows **or** the consumer scaffold's, since the skills run in both. A renamed recipe breaks the suite before it breaks an operator mid-release.

Extraction follows `test_scaffold_lint`'s doctrine — only code regions are scanned, so prose like "just merge the PR" is never read as a recipe named `merge`. The extractors are themselves unit-tested against constructed fixtures (`test_just_extractor_flags_an_unknown_recipe`, `test_yml_extractor_flags_an_unknown_workflow`), so a green suite still proves the rules can fail.

Also asserted: manifest and marketplace schema shape, no unsupported top-level keys, `.claude-plugin/` containing only `plugin.json`, the exact skill catalogue, frontmatter (name matches directory, description within the 1536-char limit), `disable-model-invocation` on every mutating skill and *not* on `status`, that every mutating skill's `/devkit:status` lookup textually precedes its first dispatch, per-skill refusal coverage keyed on issue number, every axis `/devkit:status` must report, that `status` does not hard-code `-rc`, and that the plugin is never added to `scripts/manifest.toml` or vendored into `assets/workspace/`.

## Additional Notes

**Deliberately out of scope**, matching #1744's own open questions:

- **No `commands/` wrappers** (open question 2's stated preference; the docs also say to prefer `skills/` for new plugins, and a skill already runs as a command).
- **No hooks** (open question 3 defers the trust-model question to #927).
- **Marketplace home** (open question 1): this repo self-hosts now so the plugin is installable and dogfoodable on merge instead of blocking on #927. Co-locating the plugin with the workflows keeps the version pin and the verbs in one place, which is the whole point; #927 can list it from `vig-os/org-config` with a `git-subdir` entry without anything moving.

**Coordination with #1746** (Rust release-extension seams, in flight on `feature/1746-rust-release-extension-seams`): the `release.yml` edit here is nine self-contained lines inside the existing `.vig-os` bump step, so a merge conflict with that branch should be trivial. `/devkit:status` and `/devkit:release-candidate` treat a pre-release as `<base>-<anything>` and read `DEVKIT_PRERELEASE_FORMAT` rather than assuming `-rc*`, so they stay correct when #1746 makes the format configurable. `/devkit:pack-rust` names #1746's three contracts as open work and will encode them once it lands.

**First adopter** (open question 5): devkit itself. The skills are written against devkit's own guards, and `/devkit:status` branches explicitly where the consumer scaffold differs (no GHCR gate, no cross-repo smoke gate, floating-tag guard instead of the `:latest` guard, no release-neutral lane).
