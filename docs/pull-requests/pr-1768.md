# [PR 1768](https://github.com/vig-os/devkit/pull/1768) feat: advance a pinned devkit flake input on upgrade and gate scaffold/toolchain skew in CI

## Description

In `direnv`/`both` mode the scaffold and the toolchain are versioned twice: `.vig-os`
`DEVKIT_VERSION` drives the scaffold, the devkit flake input's ref drives the dev shell. An
upgrade only moved the first, so a pinned consumer ran the previous release's tools against
the new scaffold — surfacing as `prepare-changelog seed: invalid choice` mid-release
(vig-os/scitadel#225) and as `shellcheck-composite-actions: Failed to spawn` on the
adoption PR itself (vig-os/tessera#445, #1756). The installer's `flake-bump: skipped`
line was the only signal, and no gate could see it: `flake.nix` is a `PRESERVE_FILE`.

This PR closes the gap on both axes:

- **`DEVKIT_FLAKE_PIN_ADVANCE`** (`.vig-os`, `true | false | empty`; empty = today). With
  `true`, `install.sh --force` rewrites a pinned RELEASE ref (`?ref=X` or `/X`, form
  preserved) to the new `DEVKIT_VERSION` and runs `nix flake update <input>` in the same
  step. Atomic: if the lock update fails, or `nix` is absent, `flake.nix` and `flake.lock`
  are left byte-identical. Non-release pins (`main`, `rev=<sha>`, `refs/tags/X`) are never
  touched. Every outcome prints exactly one `flake-bump:` line; the adoption PR body already
  carries it, and the knob-off line now names the key.
- **CI gate.** The scaffolded `ci.yml` gains a `Check flake pin lockstep` step in the
  `resolve-toolchain` job (which now sparse-checks-out `flake.nix`). A pinned release ref
  that differs from `DEVKIT_VERSION` fails the job with an actionable `::error::`; floating
  inputs, non-release pins (warning only), `bare` and `devcontainer` modes are never gated.
  It is deliberately independent of `DEVKIT_DRIFT_CHECK`.

`devkit-upgrade.yml` needs no change: it installs nix, commits with `git add -A`, and lifts
the `flake-bump:` line into the PR body already.

### Added

- **DEVKIT_FLAKE_PIN_ADVANCE: advance a pinned devkit flake input on upgrade**
  ([#1752](https://github.com/vig-os/devkit/issues/1752), [#1756](https://github.com/vig-os/devkit/issues/1756))
  - New `.vig-os` key `DEVKIT_FLAKE_PIN_ADVANCE`. With `true`, an
    `install.sh --force` upgrade in direnv or `both` mode rewrites a pinned
    release ref (`?ref=X` or `/X`, form kept) to the new `DEVKIT_VERSION` and
    runs `nix flake update <input>` in the same step. If the lock update fails,
    `flake.nix` and `flake.lock` are both restored. Empty or `false` (default)
    leaves a pin untouched, and the `flake-bump:` line now names the key
  - The scaffolded `ci.yml` fails its `resolve-toolchain` job when a pinned
    release ref differs from `DEVKIT_VERSION`, so an adoption PR can no longer
    wire hooks the pinned toolchain cannot run. Floating inputs, non-release
    pins, `bare` and `devcontainer` modes are not gated
  - Pinned consumers: the adoption PR that ships this gate is red once. Fix it
    in one commit on that branch (bump the pin, `nix flake update <input>`, set
    the key) and merge it before the next weekly upgrade run replaces the
    branch; see `docs/MIGRATION.md`

## Additional Notes

- **Rollout.** Pinned consumers today: h5v, revkit, tessera (all at 1.17.0/1.17.0), scitadel
  (`main` still 1.6.0). Their adoption PR to the release that ships this is red at the new
  gate once, by design (its scaffold predates the opt-in). Remedy is one commit on the
  adoption branch — bump the pin, `nix flake update <input>`, set the knob — merged before
  the next Monday 06:00 UTC `devkit-upgrade` run, which force-updates that branch. Pre-setting
  the knob on the default branch ahead of the adoption is safe only for
  `DEVKIT_DRIFT_CHECK=false` consumers: the scaffold-drift job re-scaffolds at the current
  version, which drops the unknown key.
- **#1756** stays open until that first red→green adoption is observed live; the remedy is
  posted there.
- **Out of scope, noted:** commit-action's inverse skew (`DEVKIT_VERSION=1.12.0` with a
  floating input — a consumer chore, `devkit-staleness` covers it); a `--no-write-lock-file`
  on `devkit-upgrade.yml`'s `nix develop -c git commit` (pre-existing floating-path hazard,
  not triggered by this PR's atomic advance); Proposal B (advance when the pin equals the
  outgoing version) — deliberately not done, a pin held at the outgoing version is not proof
  of intent.
