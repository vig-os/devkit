# [PR 1728](https://github.com/vig-os/devkit/pull/1728) fix(init): anchor a preserved-hook insert on the nearest present predecessor

## Description

Two defects in how a new scaffolded hook reaches a consumer's preserved `.pre-commit-config.yaml`, both exposed by the `1.17.0 shellcheck-composite-actions` row from #1726.

**A disabled anchor blocked the hook after it.** The insert anchored on the single hook the template places immediately before the new one. For the composite hook that is `actionlint`, so a consumer pinned below 1.17.0 with `DEVKIT_FEATURES_DISABLED=actionlint` had no anchor and was skipped with a warning on every upgrade, forever — while a fresh scaffold with the same opt-out does get the hook, since it sits outside the actionlint sentinels. Now `template_hook_anchors` returns every predecessor nearest-first, the insert walks them and anchors on the first one present in the consumer's file, and the warning fires only when none is. The chosen anchor's range is still whatever `hook_block_range` prefers — the sentinel range where one exists — so an insert after a present `actionlint` still lands after `# <<< devkit:actionlint`, outside what the feature's excision deletes.

**The inserted block lost its rationale.** An un-sentinelled template entry was extracted byte-exact from its `- repo:` line, so the consumer's copy carried none of the prose above it. The structural branch of `hook_block_range` now sweeps upward over the contiguous run of whole-line comments, stopping at a blank line, a non-comment line, or either sentinel marker, so it can neither swallow the previous block's text nor half a sentinel pair. Only the range's start moves; the anchor path reads the end.

**Why not sentinel-wrap the composite entry instead** (the alternative noted on the issue): sentinels mean feature-gated excision, and the composite hook belongs to no group. Decisively, `hook_block_range` matches sentinel ids by prefix, so a `# >>> devkit:shellcheck-composite-actions` marker would satisfy a lookup for `shellcheck` — breaking the very fallback that anchors on it. Verified against a fixture; recorded in the function's docstring so nobody takes that route later.

**Behaviour change to be aware of:** a pin at or below 1.16.0 whose config lacks the actionlint block now gains the composite hook through the `shellcheck` fallback. That is the fix, not a #1651 regression: those pins have never seen the composite hook (its row is 1.17.0); the actionlint row itself still stands down at 1.16.0. Two existing assertions were narrowed to `preserved-hook-insert: actionlint` for that reason, with docstrings saying why.

## Changelog Entry

### Fixed

- **Preserved-config hook inserts survive a disabled anchor and keep their
  rationale** ([#1725](https://github.com/vig-os/devkit/issues/1725))
  - A new scaffolded hook was inserted into a preserved `.pre-commit-config.yaml`
    after the single hook the template places immediately before it, so a consumer
    pinned below 1.17.0 with `DEVKIT_FEATURES_DISABLED=actionlint` had no anchor
    for `shellcheck-composite-actions` and lost the hook to a warning on every
    upgrade, forever — while a *fresh* scaffold with the same opt-out does ship it.
    The insert now walks every predecessor the template declares, nearest first,
    and anchors on the first one the file carries (here `shellcheck`); the warning
    is reached only when the file carries not one of them. A present anchor still
    wins, and still contributes its **sentinel** range where it has one, so an
    insert after a bracketed block lands past its closing sentinel rather than
    inside the range a feature excision deletes
  - An un-sentinelled template entry was extracted from its `- repo:` line down,
    so the prose above it — why the hook exists, what it deliberately does not
    cover — stayed in the template and the consumer's copy arrived as an
    unexplained `entry:`. The structural extraction now takes the run of
    whole-line comments directly above the entry too, stopping at a blank line, a
    non-comment line or a `# >>> devkit:` / `# <<< devkit:` sentinel, so no copy
    can swallow the previous block's text or half a sentinel pair
  - The retired-block **fold** reads the same extraction, so a replacement block
    now arrives with the template's rationale as well — which is what you want when
    a hook's form changed under you. Your own comment above the retired block is
    yours and is untouched, so an adoption PR shows the two comment blocks stacked
