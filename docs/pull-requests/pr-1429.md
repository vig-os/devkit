# [PR 1429](https://github.com/vig-os/devkit/pull/1429) feat(nix): Rust language pack — capability module + lib.mkRustProject

Ships the Rust language pack as **two pieces**, and the split between them is the design. Implements the `A + D + assert` resolution recorded in #1427.

Closes #1400. Refs #1427.

## How to test it

```nix
# flake.nix
inputs.devkit.url = "github:vig-os/devkit/feature/1400-rust-language-pack";

# perSystem
rust = devkit.lib.mkRustProject {
  inherit pkgs;
  src = ./.;
  toolchainHash = "sha256-…";       # for your rust-toolchain.toml
  crates = [ "my-cli" ];
};
devShells.default = rust.devShell;
checks             = rust.checks;
packages           = rust.packages;
```

Set `toolchainHash = pkgs.lib.fakeHash` first; the build failure prints the real one.

Toolchain-only, no check suite — deliberate and explicit:

```nix
modules = [ { name = "rust"; checks = "none"; } ];
```

And the thing that should NOT work:

```nix
modules = [ "rust" ];   # eval error, by design — see below
```

## What's here

| File | |
|---|---|
| `nix/modules/rust.nix` | v1 capability module: toolchain + curated cargo tooling + mold on Linux |
| `nix/mk-rust-project.nix` | `lib.mkRustProject` — dev shell, checks and packages from one call |
| `nix/modules/check-entries.nix` | internal: how the generated `module-<name>` check instantiates a module whose options are mandatory |

Checks produced: the per-crate builds, plus `clippy`, `fmt`, `nextest`, `doc` (rustdoc warnings denied) and `deny` (auto-enabled when a `deny.toml` exists).

## Why checks are a lib function and not a contract field

`packages` / `env` / `shellHook` fold monoidally into **one** derivation — the shell. `checks` is a namespaced map of **independent peer derivations** on a different lifecycle (`nix flake check`, not `nix develop`), built from the consumer's source tree, which is project shape a module never sees.

The test that settled it: a `checks` field could be added to the shell-composition contract **without touching shell composition at all**. If a field can be added to a contract without touching what that contract composes, it isn't part of that contract.

So `mkRustProject` composes *above* `mkProjectShell` and returns all three together. One call — there is no second function to forget.

## Why the module refuses to load bare

`modules = [ "rust" ]` would hand you a toolchain, a green `nix flake check` that builds nothing, and CI that compiles nothing: the exact silent-green failure the pack exists to prevent, delivered by the pack. So the module's `checks` option is **mandatory with no default**, and the bare form throws at eval with a message naming the fix and the opt-out.

Being straight about the limit: **flake outputs are consumer-assigned by construction.** No option here — including extending the contract — could have made correct wiring structurally impossible. What this shape buys is one call instead of two, `checks` arriving visibly beside `devShell`, and a loud eval-time failure on the one remaining path. Silence was the failure mode; silence is what's removed.

## Costs, stated plainly

- **`crane` + `fenix` become devkit inputs — 3 leaf lock entries that every consumer pays for**, Python-only ones included, in lock size and fetch-at-eval. The alternative is each Rust repo pinning its own fenix, which is per-repo drift on exactly the axis devkit exists to hold still. `mkRustProject` takes `crane`/`fenix` overrides, so the inputs can move back out later without a consumer-visible change. **Flag it if you disagree — this is the most reversible-but-annoying-later decision in the PR.**
- `nix/lib/` turned out to be **gitignored** (`.gitignore:17` has a bare `lib/` from the Python layout, which swallows any `lib` directory at any depth). The file lives at `nix/mk-rust-project.nix` instead, matching `nix/hooks.nix` / `nix/devtools.nix`. Worth fixing that pattern separately — it will bite someone else.

## Verified, not assumed

- `checks.<system>.module-rust` evaluates ✅
- Bare `modules = [ "rust" ]` throws the guidance error ✅
- **Zero-module invariant holds**: `devShells.<system>.default.drvPath` is byte-identical to `dev` ✅
- End-to-end on the first consumer (`gerchowl/filesender`, a cli + mcp + lib workspace): its ~120 lines of hand-rolled crane/fenix wiring were deleted and replaced by one `mkRustProject` call; all 9 checks evaluate and build.

## Two bugs this shape prevents by construction

Both were shipped by the first consumer, and both were invisible to inspection:

1. `deny.toml` outside the crane fileset — an `openssl` ban that banned nothing.
2. `clippy.toml` outside the fileset — the sandboxed clippy check ran against defaults, enforcing rules nobody wrote.

`mkRustProject` folds the well-known root tool configs (`rustfmt.toml`, `clippy.toml`, `deny.toml`, `about.*`, `.cargo/`) into the fileset unconditionally via `maybeMissing`, so there is nothing to remember and nothing to keep in sync.

## Found by devkit's own gates, on devkit

Worth recording because it is the same failure class this PR is about. My first branch was `feat/rust-language-pack` and the first two commits said `Refs #1400` without the colon. Both were **wrong by devkit's own rules** — the taxonomy is `feature`, not `feat`, and `Refs:` is a mandatory trailer — and both went through, because a fresh `git clone` has no hooks installed until something installs them. They were caught only when the hooks happened to be present for the third commit.

That is exactly the shape of the five bugs in the first consumer's history: configured, believed active, never executed. Branch renamed, trailers normalized, commits signed. But **a fresh clone of devkit does not enforce devkit's rules until someone runs the installer**, and nothing tells you that. Probably worth its own issue.

## Review asks

1. The **`crane`/`fenix` as devkit inputs** tradeoff above.
2. `check-entries.nix` — is a per-name generator override the right answer for mandatory-option modules, or should the generated smoke check learn about them some other way?
3. Whether the eval-time refusal is too aggressive for a scratch-shell user (the opt-out is one attrset, but it *is* friction).

## [Comment #2](https://github.com/vig-os/devkit/pull/1429#issuecomment-5264926223) by [@gerchowl](https://github.com/gerchowl)

_Posted on August 12, 2026 at 09:32 AM_

### Second consumer: `gerchowl/squelch` — a single-crate library

Adopted this branch on a repo deliberately unlike filesender: **one library crate, no binaries, no workspace, heavily feature-gated** (`browser`/`logs` default; `gh-cli`, `endpoint`, `serde` optional). Wired from scratch — no prior crane/fenix to delete — so this is the cold-start path rather than the migration path.

End state: **`nix flake check` green on all five checks** (`fmt`, `clippy`, `nextest`, `doc`, `workspace`) plus `packages.default`, locked against the pushed branch.

Getting there took two blockers, and both were things the pack could say out loud.

---

#### 1. `rust.devShell` does not evaluate without `devkit.overlays.default` — but the checks do

The README snippet in this PR says `inherit pkgs`, unqualified. A consumer's natural reading is their own nixpkgs:

```nix
pkgs = import nixpkgs { inherit system; };
```

which yields:

```
error: undefined variable 'vig-utils'
       at .../nix/devtools.nix:36:21
          36|   (pkgs.lib.lowPrio vig-utils)
```

An error inside devkit, naming a variable the consumer has never heard of, from a file they did not open. The fix is `overlays = [ devkit.overlays.default ]`, which is documented in `docs/NIX.md` for `mkProjectShell` but is not in this PR's usage snippet — and `mkRustProject` is the entry point that is supposed to mean you don't have to know about `mkProjectShell`.

**The part worth fixing rather than documenting:** `checks` and `packages` evaluate *fine* without the overlay, because they never touch `mkProjectShell`. So the failure mode is a repo whose `nix flake check` is green and whose `nix develop` is broken. That is the same split-brain the pack exists to close, one layer up.

Suggestion: `mkRustProject` knows whether the `pkgs` it was handed carries the overlay (`pkgs ? vig-utils`). A `throw` in mkRustProject's own voice — the `toolchainHash` error is the model, it is genuinely the best error in the codebase — costs one `if` and removes the whole class.

#### 2. A library that gitignores `Cargo.lock` is dead on arrival, and `cargoVendorDir` is unreachable

squelch's `.gitignore` had `Cargo.lock` — the long-standing library convention, and what `cargo new --lib` produced for years. A flake's `src = ./.` is the **git tree**, so the lock was simply absent from `cleanSrc`, and five of six derivations failed at eval:

```
error: unable to find Cargo.lock at /nix/store/…-source
```

crane's message is good and names `git add -N Cargo.lock`. Two things the pack adds on top:

- **The other two remedies crane suggests are unreachable.** `mkRustProject` has no `cargoVendorDir` argument, and `crateOverrides` only reaches `buildPackage` — not `buildDepsOnly`, `cargoClippy`, `cargoNextest` or `cargoDoc`. A consumer who genuinely cannot commit a lock has to abandon the function and rebuild it from the exposed `craneLib`/`commonArgs`.
- **`fmt` passes anyway** — it is the one check that takes only `src`. Check one thing first and you see green.

Same suggestion: `builtins.pathExists (src + "/Cargo.lock")` and a throw that says *why* a library repo in particular hits this. It is a one-line guard for a failure that reads as "the pack doesn't work" rather than "your lockfile isn't staged".

---

#### 3. Nothing runs doctests — #1400 promised they would

The stage table in #1400 says pre-push carries `nextest` **+ `cargo test --doc`**. This PR ships `cargoDoc` (rustdoc lints, `-D warnings`) but nothing executes doctests, and nextest cannot by design.

squelch has three executing doctests, including the `provenance!` macro example, which is the crate's main API surface. **Adopting the pack removes them from CI**, silently, on a repo where `cargo test` ran them.

`crane` already ships `lib/cargoDocTest.nix`. This looks like one more `lib.optionalAttrs` block beside `doc`.

#### 4. Default features only, and no supported way to widen

| | tests run |
|---|---|
| `cargo test --all-features` (squelch's actual suite) | 59 |
| `cargo test` (default features) | 55 |
| **the pack's `nextest`** | **55** |

Plus 0 of 3 doctests, per §3 — so 55 of 62 signals.

The four missing tests cover `gh-cli`, `endpoint` and `serde`, and more importantly **clippy never compiles that code at all**. For a crate whose README sells `default-features = false`, the pack's green is narrower than the repo's own `cargo test` — and nothing says so.

`clippyExtraArgs` exists, but there is no `features` / `cargoExtraArgs` knob reaching `buildDepsOnly`, `nextest`, `doc` or the package builds.

**What works today**, found by reading the source rather than the docs:

```nix
buildEnv = { cargoExtraArgs = "--all-features"; };   # → 59 tests run
```

`buildEnv` is documented as "For CMAKE_*, PKG_CONFIG_PATH, etc." but is merged verbatim into `commonArgs`, so it is a general crane override wearing an env-var name. It works, it is the only seam, and it is the kind of thing that gets removed in a refactor because the docstring says it holds env vars. Worth either promoting to a real `cargoExtraArgs`/`features` argument, or renaming what it is.

(Note it would also collide with `buildCrate`'s own `cargoExtraArgs = "-p ${name}"` on a workspace — squelch is single-crate so it did not bite here.)

---

#### Claims I checked, which held

- **"3 leaf lock entries."** Exact. `origin/dev` 11 nodes → this branch 14: `crane`, `fenix`, `rust-analyzer-src`. `flake-utils`/`systems` were already there.
- **The bare-module refusal fires**, and the message is the right length and says the right things. It cost me nothing in practice — I only hit it by deliberately testing it.
- **`toolchainHash = fakeHash`** → build prints the real hash → paste → works, first try. The error text explaining *why there is no sensible default* is why it took thirty seconds instead of a search.
- **The `doc` check found real defects on first execution**, exactly as it did on filesender. Two broken intra-doc links in squelch's `main`, both pointing at `endpoint`-gated items from ungated docs (`crate::Auth::Dynamic`, `Transport::Endpoint`) — so they were broken for every default-features reader. Nothing else in the repo's suite looks at rustdoc. Fixed in the consumer.

#### Answers to the three review asks

1. **crane + fenix as devkit inputs** — from a consumer's seat, keep them. Three entries is cheap, and the alternative is every Rust repo pinning its own fenix, which is per-repo drift on the exact axis devkit exists to hold still. The reversibility note in the PR (overrides exist) is the right safety valve.
2. **`check-entries.nix`** — reads fine. A name-keyed override, small, with a comment stating the bar for adding one. The `rust` entry using `checks = "none"` is honest: the smoke check owns no source tree, which is precisely the sanctioned opt-out case.
3. **Is the eval refusal too aggressive?** No — and I would say the opposite is the finding. The refusal never fired in normal use. The thing that actually cost me time was §1, which is *silent* and produces a half-working repo. Spend the aggression there.

#### Incidental confirmation of #1400's ask 3

The nix-detection false-negative is real and I hit it without looking for it: squelch is a single-`flake.nix` repo, so it is never nix-detected, never gets the nix `.gitignore` fragment, and the first `nix build` left an untracked `result` symlink in `git status`. Had to add `/result` + `/result-*` by hand. Every direnv-mode Rust consumer will do this, because a Rust pack repo is a single-flake repo by construction.

#### Two smaller notes

- **Darwin noise:** building the fenix toolchain prints dozens of `install_name_tool: command not found` lines. The toolchain works, but on a first adoption it reads as a broken build for about a minute.
- **Shell weight:** a pure-Rust library's `nix develop` carries the full devkit toolchain SSoT — `podman`, `nodejs`, `uv`, `python3`, `ruff`, `pymarkdownlnt`, `bats`, `neovim`, `tmux`, `claude-code` — ~45 packages, of which the Rust pack contributes 7. That is devkit policy rather than a pack bug, and it is the first thing a Rust-only consumer notices.

## [Comment #4](https://github.com/vig-os/devkit/pull/1429#issuecomment-5265088173) by [@gerchowl](https://github.com/gerchowl)

_Posted on August 12, 2026 at 09:48 AM_

### Added: performance tooling + a ratchet, and the #1440 partial landing

#### 1. `rust-analyzer-src` followed away (from #1440)

The one thing all four #1440 reviewers agreed on, landed independently of the open question there. Lock nodes **15 → 14**, fetched source **~33 MB → ~5 MB**.

It fed only fenix's *nightly* rust-analyzer derivation, which this pack never builds — `fromToolchainFile` takes components from the release-channel manifest. Verified by building filesender's toolchain (whose `rust-toolchain.toml` lists `rust-analyzer`) with the follows in place: `rust-analyzer` is still in `result/bin`.

**Whether crane and fenix belong in devkit at all is still open in #1440** — this PR does not settle it. That question now has four reviews and a consolidated recommendation to move them *out*; I have held it because it is a convention call for the ADR owner, not mine.

#### 2. Tool groups

`tools` entries may start with `@`:

| group | contents |
|---|---|
| `@perf` | samply, cargo-flamegraph, hyperfine, cargo-criterion, cargo-bloat, cargo-llvm-lines, cargo-show-asm + heaptrack/valgrind/poop on Linux |
| `@perf-async` | samply, tokio-console, hyperfine |
| `@api` | cargo-semver-checks, cargo-expand |

samply leads `@perf` because it is the 2026 default: sampling, no root, no `perf_events`, works on Linux and macOS.

A **group** skips members this platform lacks; an **explicitly named** tool does not. That asymmetry is the reason groups exist — asking for `@perf` is asking for this platform's kit, but naming `heaptrack` is a request that can only be met or refused, and silently dropping it hands someone a shell missing the tool they asked for. Otherwise every consumer hand-writes the same `optionals isLinux` and some get it wrong.

#### 3. The ratchet — `checks.perf-ratchet`

Auto-enabled when `.repo/perf-baseline.toml` exists (same adopt-by-existing rule as `deny`). `packages.perf-seal` emits the baseline file itself, so sealing is never hand-transcribed.

**It times nothing, on purpose.** Wall-clock benchmarks on shared CI runners move more with neighbours and thermal state than with most real regressions, and a gate that fires on noise is one people learn to re-run until it passes. The pack ADR already says coverage is reported and never gated; this is the same reasoning, harder, because a flaky perf gate teaches `--no-verify`.

What it measures is deterministic given a locked toolchain and lockfile:

- **shipped binary size**, per binary
- **dependency-graph size**, read from `Cargo.lock` at eval

Neither requires anyone to author a benchmark — which is the point. A ratchet nobody has to write is a ratchet that is actually in place. Repos doing real performance work add criterion/divan benches and run them off the CI critical path; `@perf` puts that kit on PATH.

Growth past the tolerance (default 5%) fails; a measured shrink is **reported** so the win can be banked. The baseline is committed, so the diff records who spent the budget.

#### Verified by firing it, not by reading it

On filesender — sealed a baseline, confirmed green, then tightened it:

```
  REGRESS  binary/filesender = 2672624 bytes (baseline 2000000, +33%)
  ok       binary/filesender-mcp = 3629360 bytes (baseline 3629360, 0%)
  REGRESS  graph/crates = 220 crates (baseline 200, +10%)
```

Build fails, guidance prints (`cargo bloat` / `llvm-lines` / `tree --duplicates`, then re-seal). Both directions covered — fires on bad, quiet on good.

Three new tests (group expansion produces a non-identical derivation; explicit-unavailable throws; unknown group throws). **Rust set: 12 passing.** filesender: **10 checks green** against this pushed branch.

#### One more find in the consumer

Restating `tools` surfaced that `llvm-cov` was **never** in filesender's dev shell, while `just test-cov` has always named it — it would have died on "command not found" the first time anyone ran coverage. Sixth instance in that branch's history of configured-referenced-absent. Every binary its justfile names now resolves inside `nix develop`, checked by running the resolution rather than reading the list.

#### Follow-up 1 — the overlay guard needed its other half

The guard is right and the error is the best kind. But `hasOverlay = pkgs ? vig-utils` is a **proxy**: it infers "the overlay was applied" from one package name. If devkit's overlay ever renames or drops `vig-utils`, the guard starts throwing *"you did not apply the overlay"* at consumers who did — **and the shipped test would still pass, because it asserts a throw**.

That is this branch's own rule turned on the branch: a gate is unverified until it has fired on known-bad input *and* stayed quiet on known-good. `test_mk_rust_project_dev_shell_evaluates_with_the_overlay` is the second half, and it fails the day the sentinel stops tracking what it stands for.

#### Follow-up 2 — `buildEnv` → `craneArgs`

You were right to leave this to me, and right about what it was. It is now `craneArgs`, documented as what it actually is: raw attrs merged **last** into every crane derivation, beating everything above them. `buildEnv` stays accepted as a deprecated alias so squelch's flake keeps evaluating — merged after `craneArgs`, on the reasoning that anyone still passing the old name means it. Both covered by a test.

Rust suite now **19 green**. Pushed as bf32716f.

#### On your answer to review ask 1

Noted on #1440 — you are the fifth opinion and you land opposite my consolidation there, which recommended moving `crane`/`fenix` out on ecosystem-convention grounds (`git-hooks.nix`, `treefmt-nix`, `crane` itself and `dream2nix` all carry zero language-toolchain inputs).
