# [PR 1677](https://github.com/vig-os/devkit/pull/1677) feat(ci): add the scan-config sync lane for register-only changes to main

## Description

Implements the scan-config sync lane designed in #1676: carry register-only changes to `main` **without cutting a release**, gated by machine-checked proofs.

`main` and `dev` each scan their own closure against their own `.vulnixignore`, so a register amendment on `dev` leaves `main`'s nightly lane red until the next release train. The lag is structural — the register moved **32 times in 90 days** (~one per 3 days) against a roughly **weekly** release cadence — and a permanently-red security lane is the one failure mode a gate cannot afford, because it teaches you to ignore it.

Cutting a patch release was the wrong tool: `.vulnixignore` is **not an image input**, so the artifact would be identical but for the version string, while `devkit-upgrade` opened a no-op adoption PR in every consumer repo.

## Changes Made

**`.github/workflows/scan-config-sync.yml`** — opens the PR **as the release App**.

This is the crux, not ceremony. `main` requires one approving review, GitHub forbids authors approving their own PRs, and `main`'s only bypass actor is `OrganizationAdmin` — no App holds bypass, and `promote-release.yml` merges with a plain `gh pr merge --merge`. So a human-authored PR to `main` is **unapprovable by the only human there is**, which is exactly why every release PR into `main` is already App-authored (#1672, #1648, #1620). The lane borrows that one mechanism and nothing else: which commits get cherry-picked, when the lane runs, and the final merge click all stay manual.

**`.github/workflows/scan-config-guard.yml`** — proves the PR is safe.

| Gate | Proves |
|------|--------|
| **A** | Diff touches only `.vulnixignore`, `.trivyignore`, `.github/dependency-review-allow.txt` |
| **B** | `devkitImage`/`devkitImageEnv` `.drv` paths identical to `main`'s — the artifact *cannot* differ |
| **C** | **`main`'s closure is green under the proposed register** |
| **D** | Nothing already expired |
| **E** | Reports added/removed CVE IDs as a comment (never blocks) |
| **F** | No `release/*` in flight — moving `main` mid-train dismisses its approval |
| **G** | `main`'s `## Unreleased` still empty (`prepare-release`/`prepare-hotfix` require it) |

**Why the lane is additive-only, and why Gate C exists.** The register is not append-only: a pin advance on `dev` *clears* exceptions (6 of those 32 commits), and `dev`'s pin advances first. So there is always a window where `dev` has correctly deleted an exception that `main`'s older, still-vulnerable closure depends on — mirroring the file would strand that finding and turn `main` red. Gate C therefore doesn't reason about whether a removal is safe; it runs the **real** gate against `main`'s **real** closure and reads the exit code, making a stranding deletion unmergeable rather than merely discouraged.

Gate B is a proof rather than an argument about which files are image inputs, which is what keeps Gate A a cheap fast-fail instead of carrying the whole safety case.

**`.github/label-taxonomy.local.toml`** (new) — the lane's label. It goes in the repo-local extension, not the shared taxonomy: the shared file syncs into `assets/workspace/` and would scatter this label across consumers that have none of this machinery. Verified it does *not* appear under `assets/workspace/` after `sync-manifest`.

**`docs/CONTAINER_SECURITY.md`** — new "### 6. Scan-config sync lane" defence-layer section.

### Manual Testing Details

**TDD**, two commits: `afc092ae` (21 assertions, all red — `PYTEST EXIT: 1`) → `6f73f652` (implementation, `21 passed`).

The tests pin the invariants whose failure modes are silent or catastrophic rather than merely wrong:

- **Guard job carries no job-level `if`.** A job-level condition yields a *skipped* job; were the guard ever promoted to a required status check, a skipped job on a release PR would leave that PR waiting forever on a check that never reports. "Inactive" must mean *ran and passed*.
- **Gates are label-scoped, not diff-scoped.** A release PR legitimately changes `CHANGELOG.md`, `.vig-os` **and** `.vulnixignore` (via the dev merge), so a diff-keyed guard would fail **every release**.
- **Guard never writes.** `main` sets `dismiss_stale_reviews_on_push`, so a guard that pushed would discard the very approval the lane depends on. Asserted via job-level `contents: read` plus no `git push`/`git commit`/`gh pr merge` anywhere in the job.
- **Opener mints an App token**, so the PR is App-authored and the approval is legal.

`just precommit` green (exit 0, 53 hooks) — including `actionlint` + `shellcheck` over both new workflows.

**Not yet exercised end-to-end.** These are shape and lint proofs; the runtime behaviour of gates B and C (nix `drvPath` comparison across two revisions, and the nightly-artifact fast path) has not run in CI, because `workflow_dispatch` only registers from the default branch. That is the rehearsal in the next step.

## Additional Notes

**Bootstrap, and it needs your admin bypass.** `workflow_dispatch` only registers from the default branch, so the opener cannot be dispatched until it exists on `main`. After this merges to `dev`:

1. Cherry-pick `6f73f652` onto a branch off `main`.
2. Open a PR and merge it with **`OrganizationAdmin` bypass** — one time only.

That keeps both refs byte-identical so the next release merge is clean. Worth noting the bootstrap PR itself will trip **Gate A** if the guard is already on `main` (it changes workflows and docs, not registers) — but it won't be labelled `scan-config-sync`, so the guard stays inactive-and-passing, which is precisely the label-scoping behaviour above.

**Still unverified, flagged in #1676 and worth watching during the rehearsal:** `main` sets `require_extra_approval_for_unattributed_changes: true`. App-authored commits *should* be attributed to the app rather than counting as unattributed, but that has not been proven. If it bites, a sync PR would silently demand a second approval that cannot be supplied.

## [Comment #1](https://github.com/vig-os/devkit/pull/1677#issuecomment-5814295419) by [@c-vigo](https://github.com/c-vigo)

_Posted on September 24, 2026 at 12:40 PM_

Superseded by #1678.

This version baked `scan-config` into the lane's identity and used a path allowlist as its primary gate — which encodes a guess about what is published rather than proving it, and would need extending for every new kind of release-neutral change.

#1678 generalises it: the contract is now **derivation identity** (`devShells.default`, `devkitImage`, `devkitImageEnv` `.drv` paths equal to `main`'s), which proves the published artifacts cannot differ whatever the diff touched. Scan registers become just one thing the lane carries, alongside devkit's own workflows, `tests/**` and most of `docs/**`.

The scan-register safety check survives there as a content-triggered extra rather than the lane's purpose.
