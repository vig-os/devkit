# [PR 1638](https://github.com/vig-os/devkit/pull/1638) fix(security): except the libxml2 batch and re-date the curl + openssl block

Reconciles the vulnix exception register against the 2026-09-16 scan. Four
issues, two incidents, one reconciliation pass over one file.

## Incident A -- nightly red (#1636 dev / #1637 main)

A feed event, not a closure change. The 09-15 run (`34954313210`) was green on
the same pin the 09-16 run (`35080687787`) failed on, and the findings delta is
**8 added / 0 removed against exactly one package**, no expiry fired: the
libxml2 `CVE-2026-8613x`/`-8614x` batch reached the NVD feed in that window.

Only `CVE-2026-86140` crosses the gate's 7.0 threshold and takes an entry. The
other seven score 2.9-6.9 and are deliberately left out, as the glibc block
already does for its own sub-threshold pair.

The defect is a `strcat` stack overflow in `xmlSnprintfElements` (`valid.c`),
reachable only while formatting a validity error for a DTD-validated document.
NVD scores it 8.0 and the NIST analyst 7.8, both **local-vector**. libxml2 is
transitive here, and nothing in the image validates untrusted XML against a DTD.

## Incident B -- expiry warning (#1634 main / #1635 dev)

The 2026-09-23 slot is the curl 8.21.0 + openssl 3.6.3 block. Re-verified
rather than assumed: **all 16 entries are still live findings** against the
09-16 scan on both refs, so nothing is dead weight and nothing is deletable.

Re-dated to 2026-10-21. What changed is the estimate of when the lever lands,
not the assessment -- see below.

## The finding that ties them together

All three packages ride **one** nixpkgs lever:

| package | pinned | fixed in | `release-26.05` | `staging-next-26.05` |
|---|---|---|---|---|
| curl | 8.21.0 | 8.22.0 | :x: 8.21.0 | :white_check_mark: 8.22.0 |
| openssl | 3.6.3 | 3.6.4 | :x: 3.6.3 | :white_check_mark: 3.6.4 |
| libxml2 | 2.15.3 | 2.15.4 | :x: 2.15.3 | :white_check_mark: 2.15.4 |

A single open PR -- `NixOS/nixpkgs#563094`, staging-next-26.05 iteration 7 --
clears all three. Advancing the pin today changes nothing.

**Why the 09-23 block was re-dated instead of left to die on remediation:** the
block's own note bet on the 2026-09-21 advance, which assumed iteration 7
landing first. It opened 2026-09-14 and is still open; the iteration cadence
(iter 5 merged 08-18, iter 6 merged 09-05) projects the next merge to ~09-23,
*after* Monday's advance, with the `nixos-26.05` channel trailing
`release-26.05` by about a day on top. Holding 09-23 would most likely have
lapsed the block on 09-24 -- and `check-expirations` runs in `ci.yml`, not just
the nightly lanes, so that takes **every open PR** red (the #1547 failure mode).

The new block takes its own Wednesday (10-28) rather than joining the slot it
shares a lever with: co-dating would put 17 entries on one date and re-create
the single-Wednesday cliff the #1553 stagger broke up.

Grid after this PR -- one block per Wednesday, all six verified to land on a
Wednesday:

```
09-30  lower-reachability             (5)
10-07  fzf                            (2)
10-14  glibc                          (6)
10-21  curl 8.21.0 + openssl 3.6.3   (16)   <- moved
10-28  libxml2 CVE-2026-86140         (1)   <- new
2027-06-23  Class-1 shellcheck        (1)
```

All three blocks now share one exit condition and should be **deleted together**
on the advance that ships the fixed versions -- not renewed.
