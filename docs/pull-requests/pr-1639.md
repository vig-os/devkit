# [PR 1639](https://github.com/vig-os/devkit/pull/1639) feat(workspace): exempt a named set of commit types from Refs

## Description

`DEVKIT_REFS_POLICY` decides which commit types may omit the `Refs:` line, but its
"some types exempt" case is hardcoded to the literal type name `chore`. A consumer
that adds a custom type via `DEVKIT_COMMIT_TYPES` cannot exempt that type without
exempting every type — so the two knobs compose badly: you can add the type, but
not give it the Refs treatment the type was added for.

This adds `DEVKIT_REFS_OPTIONAL_TYPES`, a comma-separated (whitespace-tolerant)
FULL REPLACEMENT list of the types that may omit `Refs:`, mirroring the pattern
`DEVKIT_COMMIT_TYPES` and `DEVKIT_BRANCH_TYPES` already establish. The enum stays
as sugar; the narrower key wins.

Absent or blank resolves to `chore` — byte-identical to today's default render for
devkit and every existing consumer.

## Changes Made

The value feeds **three renderers in lockstep** — a consumer cannot patch this
locally, because CI re-derives the list from the same key:

| Renderer | File |
|---|---|
| Scaffolded `.pre-commit-config.yaml` | `assets/init-workspace.sh` — new `RESOLVED_REFS_OPTIONAL_TYPES`, resolved next to `RESOLVED_COMMIT_TYPES` so the subset guard has the approved list; `render_refs_policy` renders it |
| Flake-generated consumer hook | `nix/hooks.nix` (`refsOptionalTypesFor`, `consumer`) → `mkProjectShell`'s new `refsOptionalTypes` argument in `flake.nix` → the `.vig-os` reader in `assets/workspace/flake.nix` |
| CI's `validate-commit-range` | `assets/workspace/.github/actions/resolve-toolchain/action.yml` — the `refs-optional-types` output |

Plus the manifest surface: the key ships bare in `assets/workspace/.vig-os`, is
read before the template overwrite and written back on upgrade (else an upgrade
silently resets a consumer's exempt set and their issue-less commit type starts
failing `commit-checks`).

**Precedence.** `DEVKIT_REFS_OPTIONAL_TYPES` wins over `DEVKIT_REFS_POLICY`; the
scaffold prints a notice when both are set. `DEVKIT_REFS_POLICY=required` remains
the way to exempt nothing at all (an empty `--refs-optional-types` reads as falsy
to `validate-commit-msg` and reverts to its own `{chore}` default, which is why
`required` still travels as the `none` sentinel).

**Guards.** Entries must be lowercase alphanumerics AND a subset of the resolved
`DEVKIT_COMMIT_TYPES` — exempting a type the validator would reject anyway is a
manifest bug. The scaffold aborts loudly and `mkProjectShell` fails eval; CI warns
rather than failing the job. `hooksModule.defaultCommitTypes` is now exported so
the flake's subset assert validates against the same list the argv is built from,
rather than a fourth copy of the stock 11.

Two bugs found in self-review and fixed in `8779f34b`, each with a regression test
committed first (`59a8490e`):

- **The render must gate on the keys, not the resolved value.**
  `.pre-commit-config.yaml` is preserved across upgrades, never template-overwritten,
  so its current arg is whatever the previous render left. Skipping the `sed` because
  the resolved value happened to equal the `chore` default stranded a consumer
  *narrowing* its exempt set with the previous, wider arg locally while CI resolved
  the narrow one — precisely the local/CI divergence this issue exists to prevent.
- **Fail-safe for an exemption list means the smallest set, not the stock mapping.**
  CI's fallback on an invalid value fell back to the `DEVKIT_REFS_POLICY` mapping;
  under `DEVKIT_REFS_POLICY=optional` that switched the Refs gate off for every type
  because the narrower key had a typo. It now clamps to `chore` unless the policy is
  already narrower (`none`). This is the one place the `#1431` commit-types analogy
  inverts — there the stock list is a subset of any sane custom one, here it is not.

`docs/COMMIT_MESSAGE_STANDARD.md` is shipped to consumers and said only `chore` is
exempt; it now carries the same consumer-knob pointer the commit-types table has.

## Additional Notes

Two things deliberately left out of scope:

- **Deprecating `DEVKIT_REFS_POLICY`.** The issue allows either; keeping it as sugar
  costs one `case` arm per renderer and breaks no consumer. It also remains the only
  way to say "exempt nothing", since an empty list means `chore` to the validator.
- **The pre-existing staleness when a consumer *clears* a render key.**
  `render_commit_types` and `render_branch_types` gate on "key absent", so clearing
  the key leaves the previous render in the preserved `.pre-commit-config.yaml`.
  This PR matches that behaviour rather than diverging from it; fixing it properly
  means an unconditional `sed` guarded against the flake-hooks store symlink, across
  all three renders — a separate issue, not a drive-by here.
