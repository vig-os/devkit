# [PR 1643](https://github.com/vig-os/devkit/pull/1643) fix(workspace): render the branch guard from the workflow model both ways

## Description

`render_workflow_model` applies the `gitflow → trunk` retarget one way — it
early-returns unless the resolved model is `trunk`. For every **managed** file it
touches that is harmless: the template overwrite restores the gitflow shape on the
next upgrade and the render simply does not re-run. `.pre-commit-config.yaml` is
**preserved**, so the trunk edits stayed in it forever.

A consumer switching back to gitflow therefore lost the dev-branch guard silently:
`no-commit-to-branch` stopped blocking direct commits to `dev`, on a repo whose
`.vig-os` says `gitflow`. No error, no notice.

Last instance of the class fixed in #1640.

## Changes Made

I scoped this out of #1641 believing it spanned many files and needed its own
design. That premise was wrong, and measuring it first is what made the fix small:
every other target self-heals, so the entire stale surface is two lines of one file.

| Target | Managed / preserved | After a trunk → gitflow round-trip |
|---|---|---|
| `ci.yml`, `codeql.yml`, `sync-issues.yml`, `prepare-release.yml`, `promote-release.yml` | managed | restored |
| `.github/renovate-default.json` | managed | restored (`["dev"]`) |
| `.devcontainer/justfile.gh` | managed | restored |
| `.claude/skills/branch-naming/SKILL.md` | managed | restored |
| **`.pre-commit-config.yaml`** | **preserved** | **STALE** |

So the `.pre-commit-config.yaml` edits move out of `render_workflow_model` into a
new `render_branch_guard_model`, which runs for **both** models and renders the dev
clause *from* the resolved model instead of only subtracting it under trunk. It
goes through the `precommit_render_target` resolver added in #1640, keeping the
symlink and absent-file refusals in one place. Each direction's anchors stop
matching once applied, so a re-run is a no-op and a default gitflow scaffold stays
byte-identical to the template.

**One trap worth recording, because it silently produced a no-op fix.** GNU sed
4.10 treats a *mid-pattern* `$` in a basic regular expression as an end anchor, not
a literal. So the obvious insert pattern

```sed
s|(?!main$)(?!^(chore)|(?!main$)(?!dev$)(?!^(chore)|
```

matches nothing at all — and fails silently, leaving the file untouched. The
existing `(?!dev$)` strip only works because its `$)` sits at the very end of the
pattern. Both metacharacters are escaped in the insert pattern for that reason;
the replacement side needs no escaping, since sed gives `$`/`^` no meaning there.
The comment in the source records this so the next person does not rediscover it.

Flake-hooks consumers were never affected: their guard comes from `mkProjectShell`,
which reads `DEVKIT_WORKFLOW` at eval time (#1224/#1434) and was already correct in
both directions. It was only the scaffolded YAML that was one-way.
