# [PR 1714](https://github.com/vig-os/devkit/pull/1714) ci: scan the SBOM instead of the image tarball for the PR-CI report

## Description

After #1692 split Project Checks into lanes, the run's critical path became `Build Container Image` → `Security Scan`: 110-119 s + 336-419 s on the four most recent `dev` runs, against 244-288 s for the longest project lane. The Trivy DB cache already hits (`Cache restored from key: cache-trivy-<date>` in seconds), so the time is the 1.5 GiB tarball walk, done twice — once for the HIGH/CRITICAL/MEDIUM report (140-174 s) and once for the CycloneDX SBOM (122-152 s).

The image is now parsed once. The SBOM step runs first; the report scans that SBOM (`scan-type: sbom`), the pattern `security-scan.yml` has used since its nightly lane was built (there, the SBOM-mode scan takes 12 s). `check-expirations` moves to `python-security`, which already has the Nix/uv environment and does not wait on `build-image`, so `security-scan` also drops its 42 s `setup-env`. No new job; `summary` and its shape test are untouched.

What changes in the report: Trivy's SBOM scanning covers vulnerabilities and licenses only, so the PR-CI report no longer runs the secret scanner. Accepted (see the issue): the report is non-blocking awareness with `exit-code: 0`, the `.trivyignore` register's own RETIRED block records that the secret scanner has never found anything on this image, and the authoritative CVE gate remains the nightly vulnix lane.

**Finding-set equivalence, measured on the real image closure** (local trivy 0.72.0, warm DB, `--severity HIGH,CRITICAL,MEDIUM --ignorefile .trivyignore`):

| Pass | Wall clock | Findings |
|---|---|---|
| `trivy image --input <tar> --format json` (today) | 90.7 s | 64 |
| `trivy image --input <tar> --format cyclonedx` (new step 1) | 83.3 s | — |
| `trivy sbom sbom.json --format json` (new step 2) | 0.34 s | 64 |

`diff` of `[VulnerabilityID, PkgName, InstalledVersion] | sort -u` between image mode and SBOM mode: **empty**. Caveats: CI pins v0.74.0; the local input was the Nix `.tar.gz` output rather than the CI `/tmp/image.tar` artifact (same closure).

**Measured on this PR's CI run:** run 36151221572 — `Security Scan` **170 s** (was 336-419 s): download 8 s, SBOM 152 s, SBOM-mode report **3 s** (was 140-174 s), upload 1 s; `setup-env` gone. Critical path `Build Container Image` 112 s + 170 s = **282 s (4m42)**, against 353 s for the longest project lane (`Project Flake Gates`, 5m53 on this run), so `Security Scan` is off the critical path. The report printed the same finding set as before; `check-expirations` ran in `Python Security Scan` (57 s).

## Changes Made

`.github/workflows/ci.yml`

- `security-scan`: `setup-env` and the `check-expirations` step removed; SBOM step first (`input: /tmp/image.tar`, `format: cyclonedx`, no `TRIVY_SKIP_*_DB_UPDATE` — `--format cyclonedx` disables security scanning and never populates a DB, so the report must be free to fetch one); report step now `scan-type: sbom`, `scan-ref: sbom-cyclonedx.json`, `skip-setup-trivy: true`, same `severity`, `exit-code: 0`, `trivyignores`. The SBOM step's `if: always()` is dropped (it only survived a failing predecessor it no longer has); the upload keeps `if: always()`, name and path unchanged
- `python-security`: `check-expirations .trivyignore .vulnixignore` added right after its `setup-env`, still blocking

`tests/test_workflow_security_scan_report.py` (new, uses `tests/workflow_scaffold` helpers)

- Register check present exactly once in `python-security` and absent from `security-scan`; nothing in `security-scan` uses `setup-env` or `uv run`; SBOM step precedes the report and the report's `scan-ref` equals the SBOM step's `output`; severity / `exit-code: 0` / `trivyignores` kept; artifact keeps the `sbom-` prefix, path equals the SBOM output, upload keeps `always()`. RED on `dev`'s ci.yml: 4 failed / 1 passed

`docs/CONTAINER_SECURITY.md`

- One paragraph under the SBOM + Trivy SBOM-mode section: PR CI uses the same two steps, reports over the SBOM, no secret scanner, nightly vulnix stays authoritative
