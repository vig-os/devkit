# [PR 1678](https://github.com/vig-os/devkit/pull/1678) feat(ci): add the release-neutral lane for changing main without a release

## Description

Implements the release-neutral lane from #1676: **merge to `main` without cutting a release**, admitted only when a machine proof shows no published artifact changes.

`main` can only be written by a release — `prepare-release` and `prepare-hotfix` are the only lanes, and both cut a tag, publish a GHCR image and trigger `devkit-upgrade` adoption PRs across every consumer repo. But plenty of changes belong on `main` while altering **nothing a consumer receives**: devkit's own `.github/workflows/**` (not the scaffolded copy under `assets/workspace/`), `tests/**`, most of `docs/**`, the scan-time registers.

Two cases motivated it:

1. A `workflow_dispatch` workflow must exist on the **default branch** to be dispatchable at all — so a new workflow cannot reach `main` without a release or an admin bypass.
2. `main` and `dev` each scan their own closure against their own `.vulnixignore`, so an amendment on `dev` leaves `main`'s nightly lane red until the next train (32 register commits in 90 days vs a weekly cadence).

> Supersedes #1677, which solved only case 2 and baked "scan config" into the lane's identity. This generalises it: scan registers are now just one thing the lane carries.

## Changes Made

**`release-neutral-open.yml`** — opens the PR **as the release App**.

Not ceremony. `main` requires one approving review, GitHub forbids authors approving their own PRs, and `main`'s only bypass actor is `OrganizationAdmin` — no App holds bypass, and `promote-release.yml` merges with a plain `gh pr merge --merge`. So a human-authored PR to `main` is **unapprovable by the only human there is**, which is exactly why every release PR into `main` is already App-authored (#1672, #1648, #1620). Nothing else is automated: which commits get carried, when the lane runs, and the merge all stay manual.

**`release-neutral-guard.yml`** — proves release-neutrality.

| Gate | Proves |
|------|--------|
| **1** | No release content (`CHANGELOG.md`, its mirror, `.vig-os`) in the diff |
| **2** | `devShells.default`, `devkitImage`, `devkitImageEnv` `.drv` paths **identical** to `main`'s |
| **3** | Consumer scaffold under `assets/` byte-identical |
| **4** | `main`'s `## Unreleased` still empty |
| **5** | No `release/*` train in flight |
| **6** | Verdict comment listing the files carried |

**Gate 2 is the contract.** Equal derivation paths mean the published artifacts *cannot* differ, whatever the diff touched — a proof, not an argument about which files happen to be inputs. It is deliberately **not** a path allowlist: an allowlist encodes a guess about what is published and would need extending for every new kind of release-neutral change. It compares `devShells.default` as well as the image because a `direnv`/`bare` consumer never pulls the image — it evaluates the dev shell straight from the flake — so an image-only check would wave through a change that alters every such consumer's toolchain.

**Content-triggered extra.** When the diff touches `.vulnixignore`, the guard also replays `main`'s own nightly gate and requires exit 0. Not part of the contract — it exists because the register is not append-only: a pin advance on `dev` *clears* exceptions and `dev`'s pin advances first, so there is always a window where `dev` has correctly deleted an exception `main`'s older closure still needs.

**Docs** go to `docs/RELEASE_CYCLE.md`, beside the hotfix lane (its sibling concept). `docs/CONTAINER_SECURITY.md` carries only a pointer plus the two register-specific notes — the procedure has one home.

**Label** lives in `.github/label-taxonomy.local.toml` (new), not the shared taxonomy: the shared file syncs into `assets/workspace/` and would scatter this label across consumers that have none of this machinery. Verified it does *not* appear under `assets/workspace/` after `sync-manifest`.

## Additional Notes

**Bootstrap — needs one admin bypass.** The lane cannot deliver itself: `workflow_dispatch` only registers from the default branch. After this merges to `dev`:

```bash
git switch -c chore/1676-bootstrap-release-neutral origin/main
git cherry-pick b18329f6 3669c3b2      # NOT 5ca1764c (the changelog)
git push -u origin HEAD
```

Then open a PR and merge with **`OrganizationAdmin` bypass**, one time only. Both refs then hold identical content so the next release merge is clean, and the lane carries its own future changes from then on.

Dropping the changelog commit from that cherry-pick is required, not tidiness — carrying it would leave `main`'s `## Unreleased` non-empty and **break `prepare-release` and `prepare-hotfix`**.

**Still unverified, flagged in #1676:** `main` sets `require_extra_approval_for_unattributed_changes: true`. App-authored commits *should* be attributed to the app rather than counting as unattributed, but that is unproven. If it bites, a lane PR would silently demand a second approval that cannot be supplied — worth watching on the first live run.

Follow-up on the changelog question: **does the lane drop the record of a security exception?**

It does not — but only because of an ordering rule the runbook had left implicit, so `9958516d` makes it explicit.

Two things were being conflated:

- **The substantive record** of a risk acceptance is the `.vulnixignore` block itself — dated triage, CVSS, `nix why-depends` provenance, reachability, lever, expiry rationale. The lane puts that on `main` **immediately**, sooner than a release would.
- **The `CHANGELOG.md` entry** is the release note. It stays on `dev` and ships with the next train, which is correct Keep-a-Changelog semantics: the changelog describes releases, and a release-neutral change is in none.

So the entry is **deferred, not skipped** — *provided the change was authored on `dev` first*. If it is instead authored on a `main`-based branch, which this lane makes newly convenient, there is no `dev` commit and the entry has nowhere to live, because `main` can never hold one (gates 1 and 4). The release note is then lost outright rather than deferred. That is a real hazard the lane introduces and the runbook did not name.

Worth protecting: **10 of the last 12** `.vulnixignore` commits carried a changelog entry.

`9958516d` adds:

- The ordering rule in `RELEASE_CYCLE.md` — in the Execute block and as the **leading** runbook rule — plus a second rule spelling out that the entry is deferred rather than skipped.
- The same, mirrored in `CONTAINER_SECURITY.md`'s pointer.
- The guard **saying it in the verdict comment**, with an extra note when the diff touches `.vulnixignore`. A reminder, not a gate: the guard cannot prove a `dev` commit exists, and claiming to check what it cannot check would be worse than saying so plainly.

### Phase 3: the lane now admits changelog entries

`CHANGELOG.md` is mirrored by a pre-commit hook into `assets/workspace/.devcontainer/CHANGELOG.md`, which is baked into the image, so under the old gate 2 *any* change carrying a release note was refused — including this PR. The lane could not carry itself.

Implemented per the revised plan: **normalized derivation comparison**, `main` may carry landed-but-unshipped changes, and #590's empty-`## Unreleased` invariant is superseded.

#### Measured locally on this branch

| Attr | un-normalized (head as-is) | normalized (changelog reverted to `main`'s) | `main` |
|------|---------------------------|---------------------------------------------|--------|
| `devShells.default` | `464904d98kis3fgq6172914ksjz6nv9y-nix-shell.drv` | same | same |
| `devkitImage` | `dlsp5xm622wdrvzqf9i0hpvjik00f1ca-devcontainer.tar.gz.drv` ❌ | `d6ikbz964cpqnvahwjrc6y7g9d4blklv-devcontainer.tar.gz.drv` ✅ | `d6ikbz96…` |
| `devkitImageEnv` | `262sli4azn161b81f4ljmjvqpwa23gaw-devcontainer-image-env.drv` | same | same |

Only `devkitImage` ever moved, and only because of the changelog. The second column is the **actual gate-2 step body**, extracted from the workflow and executed with `BASE_REF=main` — exit 0, all three equal, working tree and branch restored. (The un-normalized image hash is a function of the changelog text, so it moves with every edit to the entry; the durable claim is the pair, not the number.)

#### Changes

- **Gate 2** reverts `CHANGELOG.md` and its mirror to the base's copy, evaluates the three `drvPath`s, restores the head tree, then evaluates the base. Works without a commit because `nix eval .#…` on a dirty git tree evaluates the **working tree**.
- **Gate 1** keeps only `.vig-os` (it carries `DEVKIT_VERSION`; writing a version is releasing). Both changelog paths dropped.
- **Gate 4 deleted**, not renumbered — the numbering hole is documented so earlier discussion still reads.
- **Verdict** reports changelog drift explicitly, conditioned on the diff, and shows the entry inline. Silence was the failure mode: normalization means a release note passes the contract invisibly.
- **Docs.** `RELEASE_CYCLE.md` gains *The comparison is normalized* and *`main` may carry unshipped changes*; the dev-first authoring rule from 9958516d is **demoted to a preference** (its justification — "`main` cannot hold a changelog entry" — is now false, and `sync-main-to-dev.yml` fires on `push: [main]`); `CONTAINER_SECURITY.md`'s register pointer says to carry the entry along.
- **Tests**: gate-4 test replaced by one pinning its *removal*; gate-1 changelog assertions inverted (asserted against the gate-1 **step**, since gate 2 and the verdict name the changelog legitimately); new tests for the normalization ordering and the head-tree restore; module docstring rewritten.

#### One extra fix, found while rewriting the verdict

The verdict opened with `git checkout -q -` to undo the vulnix extra's checkout — but that extra exits early when the diff leaves `.vulnixignore` alone (the common case), so `-` resolved to **gate 2's** base checkout. `git diff origin/main...HEAD` would then be empty and the "files carried to `main`" list would come out **blank**. Each step now restores the head tree itself and the verdict does no checkout at all.

#### Corrections to the design text

- `prepare-release` never inspects `main`'s `## Unreleased` — it runs on `dev` and requires *dev's* section to have content. Only `prepare-hotfix` reads `main`'s. Fixed in the docs; the earlier "both refuse to start" phrasing was wrong.
- `prepare-hotfix`'s check is **still enforced as written**, so a hotfix cut while `main` carries entries refuses to start. That is phase 1 and is not touched here; the hotfix runbook now flags it instead of claiming emptiness is "always true by construction".
