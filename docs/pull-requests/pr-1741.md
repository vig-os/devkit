# [PR 1741](https://github.com/vig-os/devkit/pull/1741) fix(smoke-gate): anchor release-PR check-wait to a SHA

## Description

The cross-repo smoke gate's `wait-release-pr-ci` job could observe a
complete, green required-check set for the release PR's *pre-push* head SHA
and let `trigger-promote-release` dispatch `promote-release.yml` while
`release.yml`'s `finalize` job's `sync-issues` push was still re-triggering
that PR's `pull_request` CI. `promote-release.yml`'s `Validate promote
prerequisites` step then refused with "PR #<n> has checks still in
progress" -- a timing race, not a content defect. Live on the 1.17.0 train
(run `36389373270`; a plain re-dispatch, run `36392110808`, passed cleanly
over identical content). Incident record: #1735.

## Changes Made

- `wait-release-pr-ci`'s poll step now holds on two conditions each
  iteration:
  1. **Release-branch quiescence** -- no workflow run `queued`/
     `in_progress` on the release branch (resolved via `gh pr view --json
     headRefName`, never reconstructed from the version). This is the half
     that actually holds the wait across the whole `finalize` ->
     `sync-issues` -> push chain, since the `Sync Issues and PRs` run itself
     is `in_progress` on the branch for as long as it takes to push.
  2. **SHA-anchored required-check read** -- `headRefOid` is read
     immediately before and immediately after `gh pr checks --required`; a
     mismatch discards the observation (no pass, no fail/cancel verdict)
     instead of judging it. This catches a push landing in the narrow
     window of the checks query itself, which a per-iteration recheck 30s
     apart would not: on the 1.17.0 incident `sync-issues` ran for ~63s
     (`06:57:29` -> `06:58:32`), longer than one poll interval.
- The confirmed SHA is now a `wait-release-pr-ci` job output (`head_sha`).
- `trigger-promote-release` gained a cheap last-mile guard step that
  re-reads the PR head immediately before dispatching `promote-release.yml`
  and fails with an explicit, actionable message on a mismatch, rather than
  surfacing the confusing downstream "checks still in progress" refusal.
  `promote-release.yml`'s own guard is unchanged and still correct -- it
  refuses before the irreversible undraft, and this PR does not loosen it.
- `docs/CROSS_REPO_RELEASE_GATE.md`: documents the new wait contract and
  adds a troubleshooting entry for the race.

Preserved unchanged: the `CLOSED` -> error and `MERGED` -> warn-and-exit-0
early outs, the `--required` filter, the "no required checks reported yet"
tolerance, the `gh pr checks` transient-failure retry, the
fail/cancel-only-when-`PENDING_COUNT`-is-0 rule, the `TIMEOUT`/`INTERVAL`
structure, and the timeout error message.

## IMPORTANT -- not live until mirrored to smoke-test `main`

`repository_dispatch` always runs the **default-branch** version of the
listener workflow (`docs/CROSS_REPO_RELEASE_GATE.md`, Contract dependencies
#2). This devkit asset change is **not** live on the smoke gate until it
reaches `devkit-smoke-test` `main` through that repo's own release cycle (or
an explicit hotfix mirror, per precedent devkit-smoke-test#345/#353). **This
is owed follow-up work, out of scope for this PR**, and should land before
the next final train that could otherwise reproduce the race.

## Audit: does devkit's own promote path need the same fix?

The issue's Notes asked whether devkit's own promote path deserves the same
audit, since `release.yml`'s `finalize` job also triggers `sync-issues.yml`
and that push can re-trigger the release PR's CI.

**Conclusion: no automated-dispatch hazard found; not changed here.**

- Devkit's own `release.yml` `finalize` job triggers `sync-issues.yml` and
  **waits synchronously for it to complete inside the same job** (see
  "Trigger sync-issues workflow and wait" / "Record post-sync branch tip"),
  before `build-and-test` and the rest of the pipeline even start. There is
  no separate "wait for green checks, then auto-dispatch promote" job chain
  like the smoke listener's `wait-release-pr-ci` -> `trigger-promote-release`.
- `promote-release.yml` is **dispatched manually by a human**
  (`just promote-release X.Y.Z`), only after: (a) smoke-test has published
  its final GitHub Release, and (b) the human approves the release PR --
  "the cycle's single human approval" (`docs/RELEASE_CYCLE.md`). Its own
  `validate` job re-checks CI green and approval synchronously at the moment
  of manual dispatch.
- A human choosing to dispatch promote in the same narrow window a push is
  landing is a possible but self-correcting mistake (the existing
  `CI_PENDING` guard refuses loudly, and a human just waits and re-runs) --
  not the systemic, unattended race #1737 describes for the smoke listener.

No follow-up issue filed for devkit's own promote path; happy to file one if
review disagrees with this read.
