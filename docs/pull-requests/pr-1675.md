# [PR 1675](https://github.com/vig-os/devkit/pull/1675) fix(security): except the second unbound 1.26.1 CVE batch in the vulnix register

## Description

The 2026-09-24 nightly ([run 35982816399](https://github.com/vig-os/devkit/actions/runs/35982816399)) went red on **both** refs again, on the same package as the day before: `unbound 1.26.0`. Two CVEs the 2026-09-23 exception did not yet carry — `CVE-2026-82717` (9.8) and `CVE-2026-81634` (7.5).

This is a **second feed event on the same upstream release**, not a closure change and not new upstream work. All three unbound CVEs — the `-81642` excepted yesterday plus these two — were published **2026-09-16** and are fixed by the same **1.26.1** release. They arrived a day apart because vulnix matches on CPE and NVD's analysis lagged: both additions were given `cpe:2.3:a:nlnetlabs:unbound` with `versionEndExcluding 1.26.1` at `lastModified 2026-09-23T19:50Z`/`19:51Z` — **after** that morning's 09:43Z scan and before this one's 09:42Z.

So yesterday's triage was not incomplete: it excepted every member of the batch that existed as a CPE match at the time.

## Changes Made

Both CVEs are added to the **existing `2026-11-04` block**, not a new one, with a dated `AMENDED 2026-09-24` addendum in the register's established append-only style (the prior risk assessment is corrected in place by the addendum, never rewritten).

**Why one block:** all three share a single death condition — the pin advance that ships unbound 1.26.1 — so they must be **deleted together**, not renewed.

**Why the date is unchanged:** the remediation lever actually *shortened* since yesterday. The `staging-26.05` backport ([NixOS/nixpkgs#565869](https://github.com/NixOS/nixpkgs/pull/565869)) has since **merged**, so `staging-26.05` and `staging` both carry 1.26.1; `nixos-26.05` (the pinned channel) and `master` still ship 1.26.0. That leaves the fix **one** `staging` → `nixos-26.05` cycle away rather than two branch hops. A shorter lever is a reason to expect this block dies early — not a reason to re-date it off its own Wednesday in the stagger grid.

**Reachability is unchanged and covers both additions.** Each is a *resolver* path — `-81634` overflows the heap during RRSet canonicalisation of a large TCP response, `-82717` corrupts it via CNAME synthesis rewriting a max TTL in the packet buffer. This closure still carries `libunbound` only (via `podman -> gpgme -> gnupg -> gnutls`, with `libgnutls-dane.so` its sole consumer), no daemon and no `unbound` binary. The pin has not moved since that provenance was verified against the built closure on 2026-09-23.

**Re-confirmed as a feed event** on the same evidence shape as the first: `flake.lock` unchanged since the 2026-09-21 pin advance (#1662) and byte-identical on both refs, this register byte-identical on both refs, the 09-21 and 09-22 scans green against these same closures, nearest grid date 2026-10-07 so nothing expired.
