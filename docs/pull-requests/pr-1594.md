## Description

The nightly scan of 2026-09-01 ([run 33493764209](https://github.com/vig-os/devkit/actions/runs/33493764209)) went red on **both** refs, opening #1592 (main) and #1593 (dev). They are the same incident: one package, `rsync-3.4.4`, a direct member of the image env (`flake.nix`).

## Changes Made

A single time-boxed block appended to `.vulnixignore`, expiring **2026-09-23**, plus the mirrored changelog entries.

**This is a feed event, not a closure change** — established before writing any entry. The previous night's scan ([run 33386509290](https://github.com/vig-os/devkit/actions/runs/33386509290), 2026-08-31) was green on the same pin, and the findings diff across the two runs is 17 added / 0 removed / no other package touched. No exception had expired either (next grid date is 2026-09-30), so nothing in this repo caused it.

**The rev-advance lever has nowhere to land today.** All 17 are fixed in rsync 3.5.0:

| Branch | rsync |
|---|---|
| `staging-26.05` | **3.5.0** (2026-08-28) |
| `staging-next-26.05` | **3.5.0** (backport [NixOS/nixpkgs#557467](https://github.com/NixOS/nixpkgs/pull/557467), merged 2026-08-29) |
| `release-26.05` | 3.4.4 |
| **`nixos-26.05`** (pinned) | **3.4.4** |

Rebuilding on any rev reachable today reproduces these findings unchanged.

**Reachability** — unusually strong for this register, and the reason a three-week window is defensible rather than merely convenient. Six of the eight are `rsyncd` **daemon-mode** defects (53791, 70461, 70463, 53802, 53784), and CVE-2026-53803 scopes its own impact to setuid or privileged-daemon installs. This image ships rsync as an interactive CLI for a single user and never starts a daemon. Only CVE-2026-70455 (receiver-side thread exhaustion driven by a malicious *sender*) and CVE-2026-53795 (`--temp-dir`/`--link-dest` escaping the destination tree, both caller-supplied) touch the real usage model, and each still requires the user to point rsync at a hostile peer.

**Expiry placement** — `2026-09-23` takes its own Wednesday per the #1553 stagger, placed *early* in the grid (ahead of lower-reachability 09-30) because this block's lever moves soonest of any entry: one `staging-next` → `release-26.05` → `nixos-26.05` hop that the weekly `update-nixpkgs.yml` advance then picks up by itself. This block is expected to **die on remediation rather than be renewed**; if 3.5.0 has not reached the pinned channel by the expiry, the gate goes red and forces a re-review with fresh evidence.
