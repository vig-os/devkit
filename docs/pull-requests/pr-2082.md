# [PR 2082](https://github.com/vig-os/devkit/pull/2082) fix(toolchain): release-lane cache parity, bounded realisation, fail-soft cachix

## Description

Release-lane jobs in direnv-mode consumers built consumer-only derivations from source and ran into their job timeout. This PR fixes that, and the hangs, Cachix hard-failures and stuck rollbacks around it (#2010, devkit part of #2077).

Root cause: only `ci.yml` passed `cachix-cache` to `setup-devkit-toolchain`. In the public stepv `prepare-release` run 43877817364, "Configure Cachix" was skipped and 0 paths came from the consumer cache. The same hour, `ci.yml` run 43880461559 pulled those same paths in seconds.

## Type of Change

- [x] `fix` -- Bug fix
- [x] `test` -- Adding or updating tests

## Changes Made

1. **Substituter parity:** all 25 scaffolded call sites now pass `cachix-cache: ${{ vars.CACHIX_CACHE }}`. Only `ci.yml` passes `cachix-auth-token`; the token and push policy stay with #1784/#1881.
   - I read `cachix/cachix-action` v17 at the pinned SHA. With a cache name and no token it installs cachix if missing, runs `cachix use <name>` and logs "Pushing is disabled". So the new call sites are pull-only. This is documented in the action header.
   - `devkit-upgrade.yml` does not call the composite; it has its own Nix install. It gets the network knobs below through the existing lockstep constant.
   - Devkit's own `.github/` uses `setup-env` and already passes `cachix-cache` everywhere.
2. **Bounded realisation:**
   - Nix's own transfer settings `connect-timeout = 15`, `stalled-download-timeout = 60` and `download-attempts = 3`. They are set on both the `extra_nix_config` path and the host `NIX_CONFIG` path, plus `devkit-upgrade.yml`, with the rationale and the Nix settings reference in a comment. The lockstep constant is extended.
   - A new `realisation-timeout-minutes` input (default 6) sets one wall-clock budget across every `nix develop` call in the dev-shell step. It uses coreutils `timeout` with a kill grace, because composite steps have no `timeout-minutes` (metadata syntax docs).
   - On expiry the step fails with `::error::… toolchain realisation exceeded N min; last nix activity: <last nix stderr line>`.
   - An exit 137 before the deadline (e.g. the OOM killer) keeps its own exit code instead of being blamed on the clock.
   - Budget: the default 6 leaves at least 4 min of every release-lane job timeout (10–20 min) for the rest of the job. The `ci.yml` lanes fill the cache and may legitimately build, so they pass their job timeout minus 4.
   - There is no shell retry around nix; retries happen per transfer.
3. **Fail-soft Cachix (#2077):** "Configure Cachix" now has `continue-on-error`. A "Report Cachix degradation" step then emits a `::warning::` naming the likely reason (cachix binary missing / cache URL unreachable / see the step log), and the realisation continues on the remaining substituters.
4. **Rollbacks don't depend on the toolchain:** a new `minimal` input. With it the action keeps only the `retry` helper in host modes, and the in-image env plus `safe.directory` in container modes.
   - With `minimal`, no Nix, dev-shell, uv tools or prek guard are set up.
   - Used by the prepare-release, prepare-hotfix and release.yml rollbacks and promote-release cleanup. Their `run:` bodies only use gh, git, jq, base64 and retry.
   - Also used by `sync-main-to-dev` check (git and retry only), whose 5-min job timeout no realisation bound fits.
5. **Docs:** the action header and input descriptions are the source of truth. `docs/MIGRATION.md` (Mode-aware CI) gets a short paragraph on `CACHIX_CACHE`, the bounds and the degradation, linking to the header.

## Changelog Entry

### Fixed
- **Release-lane toolchain setup pulls the consumer cache, is bounded and degrades softly** ([#2010](https://github.com/vig-os/devkit/issues/2010), [#2077](https://github.com/vig-os/devkit/issues/2077))
  - Every scaffolded `setup-devkit-toolchain` call site now passes `cachix-cache: ${{ vars.CACHIX_CACHE }}`, pull-only, so release-lane jobs substitute consumer-only paths instead of building them from source into the job timeout.
  - Nix network bounds (`connect-timeout`, `stalled-download-timeout`, `download-attempts`) on every runner-side Nix config, plus a `realisation-timeout-minutes` wall-clock bound that fails with `toolchain realisation exceeded N min; last nix activity: …` instead of a silent cancel.
  - A failing Configure Cachix step now warns with the reason and continues on the remaining substituters instead of failing every job.
  - Rollback and cleanup jobs pass `minimal: true` and no longer realise the dev-shell they may be rolling back from.
