# [PR 1706](https://github.com/vig-os/devkit/pull/1706) fix(ci): stop the release-neutral guard cancelling itself on label events

## Description

`release-neutral-guard.yml` triggers on `labeled`/`unlabeled` as well as the code
events, and carried **one** `cancel-in-progress` concurrency lane per pull
request, undiscriminated by event. Every label event therefore cancelled whatever
guard run was in flight — including the `opened`/`synchronize` run the label had
nothing to do with. `gh pr create --label a --label b` emits two `labeled` events
within a second, so a pull request opened with two labels left `cancelled` guard
runs on its head beside the eventual success (run history on the last PR to
`main` shows two cancelled runs stamped within the same second).

The cost today is a red cancelled run, a stale verdict comment and a wasted
runner start per label event — this guard is not a required check. But GitHub
never resolves a required context to its *latest* check run, so a single
`cancelled` run of a required name keeps a PR's status rollup red however many
successes land after it. The split is what keeps promoting this guard safe, and
this file is the reference workflow other repositories copy.

## Changes Made

**1. Two concurrency lanes per PR, split by event kind.**

```yaml
concurrency:
  group: >-
    release-neutral-guard-${{ github.event.pull_request.number }}-${{
    (github.event.action == 'labeled' || github.event.action == 'unlabeled')
    && github.run_id || 'code' }}
  cancel-in-progress: true
```

Code events (`opened`, `reopened`, `synchronize`) share the `code` lane and still
supersede each other — only the newest head matters. Label events are keyed on
`github.run_id`, so they neither cancel nor are cancelled.

*Rejected alternative*, documented in the file and pinned by a test: one lane
with `cancel-in-progress: ${{ github.event.action == 'synchronize' }}`. A
`cancel-in-progress: false` run **queues behind** the in-flight run rather than
running beside it, so a label event would wait out an in-flight 90-minute vulnix
extra — and the label event is exactly the one whose verdict must not be stale.

**The cost, stated plainly** (see Additional Notes): label runs no longer
supersede each other, so a burst of activating label events runs the gates more
than once, concurrently.

**2. The label-name gate folded into `env.ACTIVE`.**

An unrelated relabel (`area:ci`, a priority pass) now starts a run in its own
fresh lane, where it would pay for a full gate run. Scoping the two label actions
to the lane's own label makes it a cheap all-steps-skipped **SUCCESS** instead —
never a `cancelled` run. The label *set* is still read from
`github.event.pull_request.labels`, not from `github.event.label`, so an
`unlabeled` event removing `release-neutral` deactivates the gates correctly; the
`!=` clauses are what let `opened`/`synchronize` (which carry no
`github.event.label`) through. The `guard` job still carries **no** job-level
`if` — shape rule 1 is untouched.

**3. The scope report gained its missing third state.**

With the label-name gate, "inactive" no longer implies "unlabelled": an unrelated
relabel is inactive on a PR that *does* carry the lane label, where the old
two-branch report announced "no `release-neutral` label" — the opposite of the
truth, and an invitation to add a label already there. A `LABELLED` job env holds
the label set alone (`ACTIVE` folds in the event and loses the distinction), and
the report now branches three ways: active; labelled but this event is not about
it; no label at all.

**4. Gate 6's verdict is one sticky comment, and it converges.**

Several ACTIVE runs can now reach gate 6 at once, each finding no marker and each
creating its own comment. So the step does two things:

- **Upsert.** The body carries `<!-- release-neutral-guard:verdict -->`; the step
  lists the PR's comments, filters on the marker and `PATCH`es the newest match,
  falling back to `gh pr comment` when there is none. Deliberately **not**
  `gh pr comment --edit-last`, which edits the acting identity's last comment and
  for `github-actions[bot]` may hijack an unrelated workflow's. The marker is
  appended *after* the step summary is written, so the summary stays clean.
- **Converge.** After upserting, the step re-lists the marked comments and
  `DELETE`s all but the newest. However many concurrent runs posted a verdict,
  the last one to finish leaves exactly one. `pull-requests: write` — which gate
  6 already held — covers the delete.

The marker reaches jq through `env.MARKER` rather than a shell-escaped
interpolation, the listing is an explicit `--method GET` with `per_page=100`, and
`(.body // "")` keeps a `null` comment body from breaking the filter.

**5. Documentation.** The workflow header's shape rules gain a third entry and the
concurrency block states the duplicate-run trade honestly (the file is copied by
consumers, so it stays self-explaining); `docs/RELEASE_CYCLE.md`'s gate-6 row now
says the verdict is sticky.

## Changelog Entry

### Fixed

- **The release-neutral guard no longer cancels its own in-flight run on a label
  event** ([#1698](https://github.com/vig-os/devkit/issues/1698))
  - `release-neutral-guard.yml` triggers on `labeled`/`unlabeled` as well as the
    code events, and carried one `cancel-in-progress` concurrency lane per pull
    request, undiscriminated by event. Every label event cancelled whatever run
    was in flight, including the `opened`/`synchronize` run the label had nothing
    to do with; `gh pr create --label a --label b` emits two `labeled` events
    within a second, so a pull request opened with two labels left `cancelled`
    guard runs on its head beside the eventual success.
  - Label events now get a concurrency lane of their own, keyed on
    `github.run_id`, while code events keep superseding each other. Not a single
    lane with a conditional `cancel-in-progress`: `false` queues a label event
    *behind* the in-flight run — up to a 90-minute vulnix extra — and the label
    event is precisely the one whose verdict must not be stale.
  - The trade: label runs neither cancel nor are cancelled, so a burst of
    activating label events runs the gates more than once, concurrently, instead
    of superseding — three concurrent runs is the *normal* case, since the opener
    emits `opened` plus the two `labeled` events GitHub sends for one
    `gh pr create --label`. Affordable because the gates are eval-only seconds;
    only a pull request touching `.vulnixignore` pays the vulnix extra per run.
    Accepted in exchange for never leaving a `cancelled` run behind, which every
    cancellation-based alternative reintroduces.
  - `env.ACTIVE` additionally scopes the label actions to the lane's own
    `release-neutral` label, so an unrelated relabel is a cheap
    all-steps-skipped success rather than a full gate run in a fresh lane. The
    label *set* is still read from the pull request, so an `unlabeled` event
    removing the lane label deactivates the gates as before.
  - The gate-6 verdict is now one sticky comment, found by an HTML marker and
    patched in place, instead of a fresh comment per run — a stale verdict names
    files and a changelog diff that no longer exist. It also **converges**: after
    upserting, the step deletes every marked comment but the newest, so however
    many concurrent runs posted one, the last to finish leaves exactly one
    verdict.
  - The scope report gained its missing third state. With the label-name gate, a
    relabel for something else is inactive on a pull request that *does* carry
    the lane label, where the old two-branch report claimed there was no
    `release-neutral` label at all.

## Additional Notes

**Targets `dev`**, so it reaches `main` with the next train rather than through
the release-neutral lane it fixes.

**The trade-off, explicitly.** Per-run label lanes mean label runs neither cancel
nor are cancelled, so activating label events no longer supersede each other: the
opener's normal flow (`opened` plus the two `labeled` events GitHub emits for one
`gh pr create --label release-neutral`) leaves **three concurrent ACTIVE runs**,
not one. This is accepted, not overlooked:

- the gates are eval-only seconds, so the duplicated work is cheap. The single
  exception is a PR touching `.vulnixignore`, which pays the vulnix extra once
  per run;
- the visible duplication was gate 6's, and gate 6 now converges on one comment;
- every alternative is cancellation-based, and cancellation is what this issue
  exists to remove. Queueing (`cancel-in-progress: false`) is worse still: the
  label event would wait out the in-flight run it is meant to correct.

**Scope: nothing left to sweep.** `grep -rn labeled .github/workflows assets/`
returns only this workflow's own trigger and comments (plus unrelated prose in
`assets/smoke-test/README.md` and changelog history). This guard is the only
workflow in the repo *or* the consumer scaffold with a `labeled`/`unlabeled`
trigger, so the defect class has exactly one instance and it is fixed here.

**Follow-up candidate, deliberately not fixed here** (reviewer's observation):
gate 6 has no `if: always()`, so when gate 2 or the vulnix extra fails, the
verdict step is skipped and the **last positive verdict comment stays standing**
on the PR — now more prominently, since it is sticky rather than buried under
later comments. A reviewer reading the comment would see a pass the current run
did not grant. Worth its own issue: the fix is a gate-6 that always runs and
writes a refusal verdict, which changes what the comment means and needs its own
tests. Out of scope for #1698.
