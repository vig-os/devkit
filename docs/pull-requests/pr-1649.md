window. Delta is 6 added / 0 removed against exactly one package, no expiry
fired.

## Why one entry, not six

Only `CVE-2026-89161` crosses the gate's 7.0 threshold. The siblings —
`-89156` (2.9), `-89157` (5.7), `-89158` (6.5), `-89160` (3.7), `-89162` (2.9) —
are deliberately left out, as the glibc and libxml2 blocks already do for theirs.

## The assessment

CWE-590 incorrect free in `pcre2_jit_match` when a previously copied subject is
passed in as a match context. vulnix gates on MITRE's **7.4**
(`AV:L/AC:H/PR:N`); the NIST analyst scores the same defect **7.8**
(`AV:L/AC:L/PR:L`). Both **local-vector**.

`nix why-depends` gives one path, one hop:

```
devcontainer-image-env.drv
└── ripgrep-15.1.0.drv
    └── pcre2-10.46.drv
```

So `rg -P` / `rg --pcre2` on a local search is the entire exposure surface — no
daemon, no service, no untrusted input path. Whether ripgrep's `grep-pcre2`
binding can actually produce the affected calling pattern was **not** verified;
the entry accepts that ceiling rather than claiming unreachability.

`main`'s closure additionally carries pcre2 10.47 — also below the 10.48 fix, and
one entry keyed by CVE id covers both derivations.

Not vulnix over-reporting: the pinned nixpkgs applies **no patches** to pcre2
(`pcre2.patches` evaluates empty), so this is a true version match.
