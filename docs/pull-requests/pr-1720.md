# [PR 1720](https://github.com/vig-os/devkit/pull/1720) test(bats): refuse teardown_file assertions in the BATS suite

## Description

#1699 reported that a failing `teardown_file` prints `not ok` but leaves `bats` exiting 0. **That does not reproduce.** The two-line file from the issue exits 1 on the flake's bats 1.12.0 in every mode tried — plain, `-j 4`, directory target, both formatters, and the exact `nix develop --command bats t.bats; echo $?` form — and on bats 1.14.0 from the `nixpkgs-unstable` input. The exit code is set in `bats-exec-file` and propagated by `bats-exec-suite` on both the serial and the parallel path; every upstream `teardown_file` exit-code issue is closed. The pasted output in the issue lacks the `bats warning: Executed 2 instead of expected 1 tests` line bats always prints here, so the spike most likely read `$?` after a pipeline.

What is real: three paths swallow a `teardown_file` failure whole — exit 0 and no `not ok` line either — so neither a pin advance nor a TAP-grep guard (the issue's options 1 and 2) has anything to catch:

1. `setup_file` calls `skip` → the file's `teardown_file` status is discarded (deliberate upstream, bats-core#695)
2. `--filter` / `--filter-status` selects zero tests in the file → the file body never runs
3. a command fails inside a pipeline in `teardown_file` (`false | cat`) → plain bash pipeline status, no `pipefail`

So this lands only option 3: a shape pin in `tests/test_bats_shape.py` refusing `teardown_file` in `tests/bats/*.bats`, with an empty allowlist and the three swallow paths documented where the next reader will look. No file defines `teardown_file` today, so the gate starts green.
