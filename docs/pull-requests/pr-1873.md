# [PR 1873](https://github.com/vig-os/devkit/pull/1873) fix(install): scaffold direnv mode on the host without a container

## Summary
In direnv mode `install.sh` (fresh scaffold and `--force` upgrade) and `devkit-upgrade.yml` no longer need docker/podman. `install.sh` skips runtime detection and runs the pinned `init-workspace.sh` on the host from the devkit flake source (`nix flake metadata` -> `assets/`, image bake steps replayed, scratch dir removed) — the same replay as the #1870 drift check. `devkit-upgrade.yml` drops `--docker` when `.vig-os` says `DEVKIT_MODE=direnv`. devcontainer/both/bare keep the image path unchanged.

- direnv mode is taken from `--mode direnv` or the persisted `DEVKIT_MODE`; it requires an exact `--version <tag>` (`latest` is refused) and nix, jq and rsync on PATH.
- Files are created as the invoking user, so the ownership-repair container step is skipped.
- Known limitation: the installer comes from the target release tag, so a repo's automated upgrade becomes container-free once its target release ships this `install.sh`.

## Proof
Container-free run with docker/podman absent from PATH, in a scratch repo with `DEVKIT_MODE=direnv`: `install.sh --version 1.18.0` scaffolded the workspace; after committing, `--force` left `git status` clean. Tests: `tests/test_install_direnv_host.py` (dry-run plans, container modes unchanged, executed scaffold + upgrade with docker/podman stubs that fail on any call, `latest` refusal) and `tests/test_workflow_devkit_upgrade.py`.

Refs: #1871

## Cost and coverage notes
- `nix develop` of the pinned release adds about 3.8 s warm (1.18.0, store populated; measured once). A cold run additionally fetches the dev-shell closure from the binary cache and was not measured.
- The direnv smoke lane now installs Nix before the scaffold, so the release gate no longer runs the toolchain composite's install-nix branch; consumer CI on hosted runners still does.
