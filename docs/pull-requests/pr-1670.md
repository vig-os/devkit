# [PR 1670](https://github.com/vig-os/devkit/pull/1670) fix(security): reconcile the vulnix exception register after the 2026-09-23 scan

## Description

The nightly security scan of 2026-09-23 ([run 35844608653](https://github.com/vig-os/devkit/actions/runs/35844608653)) opened four issues at once: both scan lanes went red on an unexcepted CRITICAL, and the T-7 expiry notice fired for the `2026-09-30` block. This is one register problem, not four — `.vulnixignore` is byte-identical on `main` and `dev`, so the four issues are two work items across two refs.

Three commits, each with its own evidence.

## Changes Made

### 1. Except the unbound DNSSEC-validator advisory (#1668 / #1669)

`CVE-2026-81642` (9.8 CRITICAL) — a DNSKEY whose owner name is a compression pointer into its own RDATA overflows the digest buffer in unbound's DNSSEC validator.

Diagnosed as a **feed event, not a closure change**, before writing the entry: the 2026-09-22 nightly ([run 35711419780](https://github.com/vig-os/devkit/actions/runs/35711419780)) was green on **both** lanes against the same closures — the 2026-09-21 pin advance (#1662) had already merged and been scanned green — and the delta across the two runs is **1 added / 0 removed**, exactly one package per ref. No exception had expired.

The pin lever has nowhere to land: `nixos-26.05`, `staging-26.05` **and** `master` all still ship 1.26.0 with no CVE-named patch. Upstream fixed it in 1.26.1 (2026-09-16); the nixpkgs bump ([NixOS/nixpkgs#564725](https://github.com/NixOS/nixpkgs/pull/564725)) merged to `staging` on 2026-09-22 and the `staging-26.05` backport ([NixOS/nixpkgs#565869](https://github.com/NixOS/nixpkgs/pull/565869)) opened the same day and is still open — two branch hops away.

Provenance was **re-verified against the built closure**, not carried over from the 2026-07-26 unbound block's note, because that claim is what justifies accepting a 9.8:

```
nix why-depends (runtime closure of .#devkitImageEnv):
  devcontainer-image-env -> podman 5.8.6 -> gpgme 2.0.1 -> gnupg 2.4.9
    -> gnutls 3.8.13 -> unbound-1.26.0-lib
```

`nix path-info -r` reports the **`lib` output and nothing else**, the env exposes no `unbound` executable, and `libgnutls-dane.so` is the only gnutls library that references libunbound. The advisory's vector is a *resolver* digesting DNSKEYs from an attacker-controlled zone; this image ships no resolver at all. Expires `2026-11-04`.

### 2. Drop the 18 exceptions cleared by the four-package pin advance (#1666 / #1667)

The weekly pin advance `21a67dc4` -> `6d663c05` (#1662) ships curl 8.22.0, openssl 3.6.4, libxml2 2.15.4 and pcre2 10.48. All three blocks waiting on it named the **same** exit condition and shared **one** lever — the `staging-next-26.05` iteration-7 PR ([NixOS/nixpkgs#563094](https://github.com/NixOS/nixpkgs/pull/563094)), which merged to `release-26.05` on 2026-09-19 — exactly the one branch hop plus one weekly advance the 2026-09-16 re-date predicted.

Reconciled against the findings, not assumed: the `dev` lane no longer reports curl, openssl, libxml2 or pcre2 **at all**, and diffing the register against those findings leaves exactly these 18 entries with no live match. Deleted rather than renewed, four to six weeks before their `2026-10-21` / `2026-10-28` / `2026-11-04` expiries — the grid exists so entries die on remediation.

### 3. Reconcile the 2026-09-30 block after online re-verification (#1666 / #1667)

All five entries were accepted in the 2026-06-23 baseline triage with *"specifics unverified offline"*. The notice forced the re-verification it exists to force, and this time the data was available (NVD CPE configurations, per-source CVSS, nixpkgs branch contents). **The block does not survive as a block:**

| CVE | Package | Verdict |
|---|---|---|
| `CVE-2026-27820` | zlib 1.3.2 | **CPE mismatch** — moved to Class 1 |
| `CVE-2025-59777` / `-62689` | libmicrohttpd 1.0.2 | renewed -> `2026-10-21` |
| `CVE-2026-11822` / `-11824` | sqlite 3.51.2 | renewed -> `2026-11-11` |

**`CVE-2026-27820` is not this product.** It is a buffer overflow in the Ruby **`zlib` gem** (`Zlib::GzipReader`, `zstream_buffer_ungets`). NVD's only CPE is `cpe:2.3:a:ruby-lang:zlib:*:*:*:*:*:ruby:*:*` with `target_sw=ruby`, affecting gem 3.0.0 and below / 3.1.0-3.1.1 / 3.2.0-3.2.1; vulnix matched the C zlib 1.3.2 only because **1.3.2 sorts below 3.0.1**. This was the 9.8 of the set and the entry with the weakest rationale ("reachable on any decompression path") — it is a definitive false positive, so it moves to the Class 1 CPE-mismatch block on the yearly re-check rather than being renewed as a risk acceptance.

The other four are real matches but **no longer share a Wednesday**, because their levers are far apart and the stagger rule exists so a stalled review of one cannot carry the other:

- **libmicrohttpd** — the two CVEs are the *same defect double-assigned* (one NULL-pointer dereference, fix commit `ff13abc`, identical NVD descriptions), both `CVSS:3.0/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H` — **pure availability**, no confidentiality or integrity. The server is never started (podman -> systemd, systemd not PID 1), so there is no listener for a crafted packet to reach. Closest lever: 1.0.2 -> 1.0.10 ([NixOS/nixpkgs#563547](https://github.com/NixOS/nixpkgs/pull/563547)) merged to `staging-26.05` on 2026-09-15, one hop out.
- **sqlite** — FTS5 memory corruption fixed in 3.53.2, scored by VulnCheck with no NIST analyst entry, both `AV:L ... UI:R`: the attacker must get a crafted database opened *and* MATCH-queried. Furthest lever: `master` has 3.53.3, but `nixos-26.05` and `staging-26.05` both still ship 3.51.2 with no 26.05 backport open.

Every per-entry note is rewritten to the verified vector, so the register no longer carries a 9.8 justified by a guess.

### Net effect on the register

32 entries -> **15**, on six distinct Wednesdays (`2026-10-07`, `10-14`, `10-21`, `11-04`, `11-11`, `2027-06-23`), with no two blocks sharing a date.
